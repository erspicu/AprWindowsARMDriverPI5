## Response

這是一個非常深入且典型的 Windows 驅動程式開發痛點。針對你的問題，我會區分「確定的事實」與「合理推測/業界實務」，並提供務實的解決方案，絕不編造未知的數值。

### 1. `bthx.h` 到底在哪？
**【確定的事實】**
*   **不在現代公開版 WDK 中**：`bthx.h` **不包含**在 Windows 10/11 的標準公開 WDK（如你手上的 10.0.26100.0，或早期的 19041/22621）的 `shared` 或 `km` 資料夾中。
*   **歷史與定位**：Bluetooth Extensible Transport (BTHX) 模型是在 Windows 8 時代為了 SoC（如 ARM 處理器上的 UART/I2C 藍牙晶片）引入的。
*   **【推測/業界實務】** 歷史上，這個標頭檔曾短暫存在於 Windows 8.0 / 8.1 的 WDK 中，或者是作為 **BSP (Board Support Package) / IHV 專屬套件** 的一部分發布給高通 (Qualcomm)、博通 (Broadcom)、瑞昱 (Realtek) 等晶片廠。微軟將其視為「硬體廠商實作底層傳輸」的介面，而非一般應用程式或上層過濾驅動會碰到的東西，因此在 Win10 之後將其從一般 WDK 中移除了。

### 2. 怎麼取得（合法）？
**【確定的事實】**
*   **無公開現代下載點**：目前沒有任何「微軟官方、公開且合法」的 Windows 10/11 SDK/WDK 連結可以直接下載到 `bthx.h`。
*   **Windows-driver-samples**：微軟官方的 GitHub 驅動範例庫中**沒有** BTHX 的完整範例，也沒有附帶 `bthx.h`。

**【業界實務解決方案】**
1.  **自行宣告 (Stand-in Header)**：這是業界最常見的做法。微軟在官方文件（[Bluetooth Extensible Transport 參考資料](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-extensible-transport-reference)）中詳細記錄了結構體的欄位，開發者通常會依據文件自行寫一個 `bthx.h`。
2.  **考古舊版 WDK**：如果你能找到合法下載的 Windows 8.1 WDK (ISO)，可以解壓縮尋找看看，但效率不如直接自行宣告。

### 3. 如果要自己宣告（Stand-in header）的精確定義

以下是依據微軟官方文件與 WDM 驅動開發常理所整理的定義。**請注意標註為「需確認」的部分。**

#### A. 結構體與列舉 (Structs & Enums)
**【確定的事實：欄位名稱與型別，來自微軟文件】**
```c
#pragma once
#include <wdm.h>

// 藍牙 HCI 封包類型
typedef enum _BTHX_HCI_PACKET_TYPE {
    HciPacketCommand = 1,
    HciPacketEvent   = 2,
    HciPacketAclData = 3,
    HciPacketScoData = 4
} BTHX_HCI_PACKET_TYPE;

// 讀寫 Context (注意 Data 欄位是變長度的)
#pragma pack(push, 1) // 建議先用 pack(1) 測試，或依編譯器預設 (通常 ULONG 會對齊 4 bytes)
typedef struct _BTHX_HCI_READ_WRITE_CONTEXT {
    ULONG DataLen;                // Data 陣列的長度
    BTHX_HCI_PACKET_TYPE Type;    // 封包類型
    UCHAR Data[1];                // 實際 HCI Payload，長度為 DataLen
} BTHX_HCI_READ_WRITE_CONTEXT, *PBTHX_HCI_READ_WRITE_CONTEXT;
#pragma pack(pop)

// 裝置能力 (Capabilities)
typedef struct _BTHX_CAPABILITIES {
    ULONG MaxAclTransferInSize;
    ULONG MaxAclTransferOutSize;
    ULONG MaxScoTransferInSize;
    ULONG MaxScoTransferOutSize;
    ULONG MaxEventsTransferInSize;
    BOOLEAN IsDeviceImplicitlyAttached; // true 表示裝置已整合(如 SoC 內部)，無須熱插拔處理
    // 【注意】這裡可能會有 3 bytes 的 Padding 以對齊 4 bytes，
    // sizeof(BTHX_CAPABILITIES) 在編譯器預設下通常是 24 bytes。
} BTHX_CAPABILITIES, *PBTHX_CAPABILITIES;
```

#### B. IOCTL Codes (`CTL_CODE`)
**【這是最大的不確定點】**
微軟文件雖然列出了 `IOCTL_BTHX_READ_HCI`、`IOCTL_BTHX_WRITE_HCI`、`IOCTL_BTHX_QUERY_CAPABILITIES` 等名稱，但**並未公開其十六進位的 Function Code**。

*   **Device Type**: 幾乎肯定是 `FILE_DEVICE_BLUETOOTH` (`0x00000027`)。
*   **Method**: 讀寫 HCI 通常是 `METHOD_OUT_DIRECT` 或 `METHOD_NEITHER`。
*   **Function Number**: 未知。

**【務實的破解法 / 業界實務】**
既然你在做 Windows on ARM64，你手上一定有原生 WoA 的機器（例如 Surface Pro X 或 Snapdragon 筆電）。
1.  找到該機器上原廠的藍牙 UART/BTHX 驅動（例如 Qualcomm 的 `qcbtuart.sys` 或 `qca_bt.sys`）。
2.  使用 IDA Pro 或 Ghidra 將該 `.sys` 檔或 Windows 內建的 `bthport.sys` 丟進去反組譯。
3.  尋找 `IRP_MJ_DEVICE_CONTROL` 的 Dispatch Routine (或 `EvtIoDeviceControl`)。
4.  看它在 `switch (IoControlCode)` 時比對的常數值（通常是 `0x27....` 開頭的 Hex 值）。
5.  將你找到的 Hex 值直接 `#define IOCTL_BTHX_READ_HCI 0x27xxxx`，這是最精確且唯一不會出錯的方法。

*(我遵守承諾，絕不在此瞎猜一個 0x270001 給你，因為猜錯你的驅動直接收不到 IRP)*

#### C. INF 註冊 (AddReg)
為了讓 `bthport.sys` 知道你的驅動是 Extensible Transport 並將其掛載，你的 INF 檔需要以下設定：

```inf
[YourDevice_Install.NT.HW]
AddReg = Bthx_AddReg

[Bthx_AddReg]
; 宣告這是一個 BTHX Transport
HKR, , BthxTransport,  0x00010001, 1      ; 1 可能代表 UART (自訂匯流排)
HKR, , BthxProtocol,   0x00010001, 2      ; BTHX_PROTOCOL_UNKNOWN 或特定協定
; 註：具體數值 (1, 2) 視你模擬的硬體而定，可參考官方文件對 BthxTransport 鍵值的定義
```

### 4. 替代方案（如果 BTHX 走不通）

在 Windows on ARM64 上，如果你是要將一顆透過 UART (例如 H4 協定) 連接的藍牙晶片接上 Windows，**你極有可能根本不需要寫 BTHX 驅動。**

**【確定的事實】**
Windows 10/11 內建了強大的**原生序列藍牙傳輸驅動 (`BthUart.sys` 或 `Serialbus` 路由)**。

**【務實的替代做法：使用 Inbox UART HCI】**
如果你晶片的 UART 端吐出來的是標準的 HCI 封包（例如標準的 H4 格式：1 byte 類型 + HCI Payload），你可以利用 ACPI 與內建驅動，完全免寫 C 程式碼：

1.  **修改 ACPI DSDT/SSDT**：
    在 ACPI 表中，定義你的藍牙裝置是掛在某個 UART Controller (SerCx2) 下。
    設定 `_HID` (Hardware ID)。
2.  **編寫一個僅有 INF 的驅動 (Extension INF 或直接 match HID)**：
    利用 Windows 內建的 `BthUart.sys`。
    你的 INF 大致會長這樣，利用 `Include` 和 `Needs` 指令拉入內建的藍牙 UART 堆疊：
    ```inf
    [Version]
    Signature   = "$WINDOWS NT$"
    Class       = Bluetooth
    ClassGuid   = {e0cbf06c-cd8b-4647-bb8a-263b43f0f974}
    Provider    = %ProviderName%

    [Manufacturer]
    %ManufacturerName% = Standard,NTarm64

    [Standard.NTarm64]
    %DeviceName% = BthUart_Device, ACPI\YOUR_HW_ID

    [BthUart_Device.NT]
    Include = bth.inf
    Needs   = BthUart.NT  ; 呼叫系統內建的 UART HCI 處理機制

    [BthUart_Device.NT.Services]
    Include = bth.inf
    Needs   = BthUart.NT.Services
    ```
    這條路是目前 x86/ARM64 筆電上，非 USB 藍牙裝置最主流的掛載方式。只有在需要處理非標準的 UART 喚醒 (Out-of-band GPIO wake) 或特殊的韌體下載 (Patch RAM) 時，IHV 才需要寫一個自訂的 Upper Filter Driver 或是 BTHX 驅動來做攔截。

### 總結你的下一步：
1. **評估替代方案**：先確認你的晶片是否支援標準 UART H4。如果是，放棄 BTHX，改用 INF + `BthUart.sys` 方案。
2. **若必須寫 BTHX**：請使用上面的 struct 宣告，並使用 IDA 反組譯 `bthport.sys` 來取得確切的 `IOCTL_BTHX_*` 常數值，這只需花你不到一小時，卻是最踏實的做法。
