## Response

這是一份針對 Raspberry Pi 5 (BCM2712) 移植 Windows on ARM64 (WoA) 在 IOMMU (SMMU) 領域的技術釐清報告。

我會嚴格區分 **[事實]**（基於 Windows 官方架構與公開的 ARM/Linux 程式碼）、**[推測]**（基於過往高通/NXP 等 WoA 移植經驗的合理推斷）與 **[不確定]**（需要實際在 Pi 5 硬體上驗證的點），並保留標準的英文技術名詞。

---

### 1. 概念釐清：Windows on ARM64 的 IOMMU 到底是誰管？

**結論：不需要寫「IOMMU 驅動」。移植 IOMMU 實際上 ＝ 把硬體的 SMMU 拓樸正確描述進 ACPI IORT table，並確保 UEFI 將硬體初始化到 Windows 預期的狀態。**

*   **[事實] Windows 架構設計：** 在 WoA 中，ARM SMMU 的管理由 Windows 核心（HAL 層與 DMA 子系統，通常涉及 `hal.dll` 與內建的 SMMU 延伸模組）全權負責。微軟針對標準的 ARM SMMUv1、SMMUv2 (MMU-400/500) 與 SMMUv3 提供了 **Inbox support（內建支援）**。開發者**不需要**也不能寫一個第三方的 `.sys` 去取代它。
*   **[事實] Driver 開發者的視角：** 當你為 RP1 的周邊（如 USB、Ethernet）寫 WDF driver 時，只要呼叫標準的 `WdfDmaEnablerCreate`、`WdfCommonBufferCreate`。底層的 Windows DMA Framework (DMAv3) 會自動去查閱 ACPI 的 **IORT (IO Remapping Table)**。
*   **[事實] 運作流程：** Windows 查閱 IORT 找到該 device 對應的 SMMU 與 Stream ID (SID) -> Windows 在 SMMU 中建立 Page Table -> 將 Physical Address 映射到 IOVA (I/O Virtual Address) -> 將 IOVA 交回給 WDF driver -> 硬體使用 IOVA 發起 DMA -> SMMU 硬體自動轉換為 Physical Address。
*   **[推測] BCM2712 的專屬 Enablement：** 雖然不需要寫 Windows 驅動，但如果 Broadcom 在 SMMU 外圍包了 proprietary 的 power domain 或 reset controller，**UEFI (如 EDK2) 必須在 ExitBootServices 之前將 SMMU 供電並解除 Reset**，讓 SMMU 處於一個 Windows HAL 可以直接讀取標準 ARM SMMU 暫存器的狀態。

---

### 2. BCM2712 的 DMA/SMMU 拓樸

*   **[事實] BCM2712 的 SMMU 版本：** 根據上游 Linux Kernel 的 `bcm2712.dtsi` 與 Broadcom 公開資訊，BCM2712 內建的是 **ARM MMU-500**。MMU-500 實作的是 **ARM SMMUv2** 架構。
*   **[事實] Windows 的支援度：** Windows ARM64 完全支援標準的 SMMUv2 (MMU-500)。
*   **[事實] Linux DT 的描述方式：**
    *   在 Linux DT 中，SMMU 本身會有一個 node：`compatible = "arm,mmu-500"`。
    *   對於 PCIe RC (Root Complex)，會使用 `iommu-map` property。這個 property 定義了：`PCIe Requester ID (RID) -> 經過一個 offset -> 轉換為 SMMU Stream ID (SID)`。
    *   RP1 是掛在 PCIe 上的 Endpoint，所以 RP1 內部所有周邊發起的 DMA，對 BCM2712 的 SMMU 來說，都是帶著同一個（或一組）PCIe RID 進來的。
*   **[事實] 轉換為 ACPI IORT 的結構：** 為了讓 Windows 看懂，你必須在 UEFI 中編寫（或透過 ASL 編譯）IORT table，裡面必須包含至少三個 Node 且互相連結：
    1.  **SMMUv1/v2 Node**：描述 MMU-500 的 Base Address、Interrupts、Global 暫存器位置。
    2.  **PCI Root Complex Node**：代表 BCM2712 的 PCIe RC。
    3.  **ID Mapping Array**：寫在 PCIe RC Node 裡面，明確定義「PCIe RID `0x0000` 到 `0xFFFF`，對應到 SMMU Node 的哪一個 Stream ID (SID)」。

---

### 3. 如果 IORT 沒寫對會發生什麼事？

這取決於 UEFI 離開時硬體的預設狀態，以及 Windows 的安全設定（VBS / Kernel DMA Protection）。

*   **[事實] 情況 A：SMMU 處於 Bypass (Passthrough) 模式**
    如果硬體預設/UEFI 把 SMMU 設為 Bypass（或稱 Identity Map，輸入位址＝輸出位址），且 IORT 缺失。Windows 會認為這個平台沒有 IOMMU，WDF DMA 會直接回傳 Physical Address 作為 Logical Address。
    *   **結果：** DMA *可能*會成功，RP1 的 driver 可以正常運作。**但**前提是 Windows 核心分配出來的 Physical Address 落在 RP1 PCIe 控制器能定址的範圍內（如果 RP1 只能做 32-bit DMA，且拿到了 >4GB 的實體記憶體位址，DMA 會失敗或覆寫錯誤記憶體，導致藍白畫面）。
*   **[事實] 情況 B：SMMU 處於 Fault/Block 模式（或 Windows 啟動了 DMA Guard）**
    如果 SMMU 預設阻擋未經映射的交易，而 IORT 寫錯（例如 Stream ID 對不起來）。Windows 的 HAL 建立了正確的 IOVA，但寫入了錯誤的 Stream ID 暫存器。
    *   **結果：** 當 RP1 透過 WdfCommonBuffer 發起 DMA 時，封包到了 BCM2712 的 SMMU，SMMU 發現沒有對應的 translation table，會直接硬體擋下該 transaction，並觸發 SMMU Context Fault Interrupt。
    *   系統會直接 **Bugcheck (BSOD)**，通常是 `DRIVER_VERIFIER_DMA_VIOLATION` 或硬體層級的 NMI/SError。
*   **[推測] 實際影響：** 在現代 Windows 11 ARM64 中，IOMMU 幾乎是強制性的，尤其是為了支援 HVCI (Hypervisor-Protected Code Integrity)。如果 IORT 沒寫對，Windows bootloader 或 HAL 可能在極早期就會 Panic，或者導致 PCIe link up 成功但後續的 NVMe/USB driver load 時死機。

---

### 4. 務實結論：這項工作到底要做什麼？

**難度之所以被列為「高」，不是因為你要寫 `.sys` 驅動程式碼，而是因為 Debug ACPI Table 與硬體暫存器狀態極度困難。**

#### 實際工程任務清單：
1.  **UEFI 端的準備 (EDK2)：**
    *   確認 SMMU 的時鐘 (Clock) 和電源 (Power Domain) 在 UEFI 階段已經開啟，且沒有被 ATF (ARM Trusted Firmware / TrustZone) 鎖定為 Secure-only。
    *   **[不確定]** Broadcom 可能有特規的暫存器需要設定，才能把 PCIe 的 AXI 匯流排路由到 MMU-500。必須參考 Linux 的 `pcie-brcmstb.c` 或 SMMU driver 看有沒有 workaround。
2.  **編寫 ACPI IORT (ASL/C code in EDK2)：**
    *   翻閱上游 Linux BCM2712 Device Tree。
    *   找出 SMMU Base Address、Interrupt Numbers（注意 GIC SPI 中斷號碼在 ACPI 裡的 off-by-32 偏移問題）。
    *   找出 PCIe RC 的 Requester ID 到 Stream ID 的對應關係。
    *   依照 ARM DEN0049 (IORT Specification) 撰寫 IORT Table 並放入 UEFI 韌體中。
3.  **編寫 ACPI DSDT/MCFG：**
    *   IORT 只是定義映射。你的 DSDT 裡面還是要有正確的 `Device (PCI0)`，並且它的 `_CCA` (Cache Coherency Attribute) 屬性要設定正確，這會直接影響 DMA buffer 是否需要 cache flush。

#### 最大未知數 (The Catch)：
*   **RP1 本身的複雜度：** RP1 是一個掛在 PCIe 上的南橋，裡面包了無數的周邊。標準 PCIe 是用 Bus/Device/Function (BDF) 來決定 Requester ID。我們需要確定 RP1 內部的不同周邊（USB  controller vs Ethernet controller）發送 DMA 時，是共用同一個 PCIe BDF 還是各自有不同的 BDF？這決定了 IORT 的 ID Mapping 陣列要怎麼寫。

#### 參考文件 (SOURCES)：
1.  **ACPI 規範：** ARM IO Remapping Table (IORT) Specification (Document number: DEN 0049) -> *這是寫 Table 的聖經。*
2.  **Linux 原始碼：**
    *   Device Tree: `arch/arm64/boot/dts/broadcom/bcm2712.dtsi`
    *   Drivers: `drivers/iommu/arm/arm-smmu/arm-smmu.c` (確認是否有 `bcm2712` 的 quirks)
3.  **Windows 文件：** Learn Microsoft - "ACPI for ARM64" & "Kernel DMA Protection".

**總結：** 放下 DDK/WDK。去寫 EDK2 的 C code / ASL code 把 IORT 建出來，並祈禱硬體沒有被 TrustZone 藏了一手。這就是「移植 IOMMU」的真實意義。
