這是一個極具挑戰但也非常有價值的核心移植任務。針對將 BCM2712/CYW43455 (SDIO) 移植到 Windows on ARM64，以下是直接、務實的技術判斷與執行路徑：

### 1. 參考資源與開源專案

不要看 Linux `brcmfmac`，它的架構與 Linux 網路子系統耦合太深。**你應該看針對 RTOS 或微內核設計的 C/C++ 移植版本，這些版本將 Broadcom FullMAC 邏輯完全抽離了 OS 依賴。**

#### (A) Windows WiFi 框架側 (WiFiCx / NetAdapterCx)
*   **NetAdapterCx & WiFiCx (現代首選):**
    *   **GitHub Repo:** `microsoft/Windows-driver-samples`。
    *   **參考範例:** 尋找 `network/netadaptercx` 目錄下的範例（例如 `RxTxHandling` 或 `Junction`）。
    *   **WiFiCx 文件:** 微軟 Learn 上搜尋 "Introduction to WiFiCx"。這基於 NetAdapterCx，替換了舊的 WDI。
*   **WDI (WLAN Device Driver Interface - 舊版但有完整 Sample):**
    *   雖然微軟推 WiFiCx，但 `Windows-driver-samples` 裡有一個非常完整的 WDI 範例：`network/wlan/WDI/OnetNDIS` (或 IHV 範例)。這能讓你了解 Windows 期望 WiFi 驅動處理的 OID (Object Identifiers) 狀態機。

#### (B) 晶片 / 韌體側 (抽出 Broadcom FullMAC 邏輯)
*   **Infineon/Cypress Wi-Fi Host Driver (WHD) (最重要資源！):**
    *   **GitHub Repo:** `Infineon/wifi-host-driver`
    *   **說明:** Cypress 買下 Broadcom IoT 部門後，為了讓這顆晶片能跑在 FreeRTOS 等系統上，寫了一個**純 C 語言、高度可移植的驅動層 (WHD)**。它自己實作了與 CYW43455 溝通的 DHD (Dongle Host Driver) 協議、SDIO 封包封裝、韌體載入。
    *   **策略:** 你只需要實作 WHD 要求的 `cyhal_sdio_xxx` (底層硬體抽象) 和 OS timer/mutex 介面，WHD 就能幫你把晶片初始化、載入 `.bin` 和 `.nvram`，並吐出標準的 802.3 Ethernet 封包。
*   **Fuchsia OS (Google) 的 Broadcom 移植:**
    *   **Source:** Fuchsia source tree `src/connectivity/wlan/drivers/third_party/broadcom/brcmfmac/`
    *   **說明:** Google 用 C++ 重寫了 brcmfmac，架構比 Linux 清晰非常多，且完全解耦了 cfg80211。適合用來參考 DHD 協定。
*   **FreeBSD (`if_bwfm`):**
    *   **Source:** FreeBSD source tree `sys/dev/bhnd/bcma/` 和 `sys/dev/bwfm/`。這是另一個乾淨的 Unix-like 實作。
*   **Firmware & NVRAM 來源:**
    *   標準 `linux-firmware` repo (`cypress/cyfmac43455-sdio.bin` 和對應 Raspberry Pi 的 `.txt` NVRAM 配置檔)。

### 2. 降低工程量的策略與替代架構

#### 捷徑一：將 WiFi 偽裝成有線網卡 (Ethernet-like Shortcut) - 最推薦的 MVP 策略
*   **作法:** **完全放棄 WiFiCx / WDI / Native 802.11。**
*   **邏輯:** CYW43455 是 FullMAC，韌體內部自帶 WPA/WPA2 supplicant，並能直接輸出 802.3 乙太網封包。
*   **架構:**
    1. 寫一個標準的 **NetAdapterCx** (Ethernet) 驅動。Windows 會以為插了一條實體網線。
    2. 在驅動內部整合 Infineon WHD 函式庫。
    3. 把 SSID 和 Password 透過 Registry 傳給你的驅動。
    4. 驅動啟動時，透過 WHD 下達 SDIO 指令讓晶片連上 WiFi AP。
    5. 連上後，將 WHD 吐出來的 802.3 封包直接餵給 NetAdapterCx 的 Rx Queue；Tx 反之亦然。
*   **優點:** 避開了 Windows WLAN API 龐大且嚴苛的狀態機與 WHQL 認證地獄。工程量從 12 個月縮減到 2-3 個月。缺點是使用者無法在 Windows 右下角看到 WiFi 掃描列表，只能硬體連線。

#### 捷徑二：SDIO API 的處理現況
*   **Windows SDIO 堆疊:** Windows ARM64 內建了 `sdbus.sys` (SD Bus Driver) 和 `sdhc.sys` (SD Host Controller Driver)。只要你之前移植的 SDHCI (可能是 BCM2712 內部的 SDIO controller) 能被 `sdhc.sys` 認出，`sdbus.sys` 就會自動列舉掛在上面的 CYW43455。
*   **Driver Interface:** 你需要寫一個 KMDF driver，掛載為 SDIO Function Driver。你需要使用 `SdioBus.h` 裡定義的 IRP (如 `IRP_MN_READ_CONFIG`, `IRP_MN_WRITE_CONFIG`) 或 `SdBusSubmitRequest` 來執行 CMD52/CMD53 (SDIO 暫存器讀寫與資料傳輸)。

#### 廢棄的選項
*   **NDIS Native WiFi (dot11):** **絕對不要用。** 微軟在 Windows 10 以後已經強烈棄用，許多新 API 與現代待機 (Modern Standby) 支援都有問題，且寫法極其繁瑣。

### 3. 務實的工程量與風險評估

*   **人力與時間 (Senior Driver Dev):**
    *   **方案 A (偽裝 Ethernet MVP):** 2 ~ 3 人月。最大卡點在於搞懂 Windows `SdBusSubmitRequest` 的 API 行為，以及確保 SDHCI controller 的 DMA 在 ARM64 上不丟包。
    *   **方案 B (完整 WiFiCx 驅動):** 至少 6 ~ 12 人月。你要處理 WiFiCx 的 OID 轉換、Scan list 管理、Power State (D0/D3)、WPA3 offload 等，對除錯是場噩夢。
*   **最大未知數:**
    1. **OOB (Out-of-Band) Interrupt:** SDIO WiFi 通常依賴一根獨立的 GPIO 作為 Host Wakeup / RX Data Ready 中斷。在 Windows 上，這需要在 ACPI (或 Device Tree 轉譯層) 中正確定義 GPIO Interrupt resource。如果 ACPI 沒寫對，你的驅動收不到中斷，效能會極差（只能 polling）或完全不動。
    2. **SDIO 效能與 DMA Cache Coherency:** Pi 5 BCM2712 的 SDIO 控制器在 Windows 下如果沒有處理好 Cache 維護，CMD53 傳輸大塊封包時容易引發靜默的記憶體損壞 (BugCheck 0x139 或隨機藍白畫面)。
*   **最務實的替代方案 (備案):**
    *   如果專案死線逼近，只需「先求上網」：使用 **USB CDC-NCM 或 RNDIS 協議**。
    *   硬體解法：買支援標準 CDC-Ethernet 的 USB 網卡，Windows ARM64 內建 `cdce.sys` / `rndiscmp.sys`。
    *   手機 USB 分享網路：插上 Android 手機開 USB 網路分享，Windows ARM64 預設即插即用，立刻獲得外網。

### 4. 盲點與容易被忽略的相依性

1. **NVRAM 載入順序與格式:** Broadcom 晶片在下載完 `.bin` 韌體後，必須緊接著透過特定的 DHD 命令下載 NVRAM (`.txt`)。這個 `.txt` 不能有結尾多餘的空行，且必須解析成 key=value 的 null-terminated string array。格式稍微錯一點點，韌體就會在內部 Crash 且沒有任何 Log，表現出來就是 SDIO 失去回應。
2. **ACPI DSDT 描述:** 在 Linux 下，DTS 定義了 `brcmf` 節點。在 Windows，必須在 ACPI 表 (DSDT) 中將 SDHCI 下掛一個子設備，設定其 Hardware ID (`SD\VID_02D0&PID_A9A6` 之類)，OS 才會嘗試為這個 Function 尋找並載入你的 sys 檔。你們負責 ACPI 的人必須配合。
3. **Power Management (S0ix / S3):** 預期第一次實作時，只要系統休眠再喚醒，WiFi 絕對會死掉。強烈建議在 MVP 階段，在 KMDF 的 `EvtDeviceD0Exit` 裡強制把晶片重置 (Power Off)，在 `EvtDeviceD0Entry` 重新走一遍載入 Firmware 的流程。先不要嘗試搞複雜的 FW Offload Keep-Alive。

**結論總結：**
果斷放棄移植 Linux `mac80211/brcmfmac` 邏輯。直接拿 **Infineon WHD (Cypress Wi-Fi Host Driver)** 的純 C 代碼，外面包一層 **NetAdapterCx** (偽裝成有線網卡)，透過 Windows 原生的 `SdBusSubmitRequest` 將 SDIO CMD 送進去。這是你們在有限時間內能在 Windows ARM64 上點亮 CYW43455 的唯一捷徑。
