### Q1: Visual Studio MSBuild Integration via Winget

**No, the winget installation does not reliably install the Visual Studio MSBuild integration.** 
The WDK installer extracts the components, but injecting the MSBuild toolsets and Project Types into Visual Studio requires installing a VSIX extension. In headless or command-line (winget) installations, the VSIX installation often gets skipped silently (especially if Visual Studio is currently running, or due to lack of elevation prompts).

You usually need to install the VSIX manually. It is left on your disk by the WDK installer here:
`C:\Program Files (x86)\Windows Kits\10\Vsix\VS2022\10.0.26100.0\WDK.vsix`

**EXACT paths to check for successful MSBuild integration:**
If the integration is installed correctly, the following paths **must** exist:

1. **Platform Toolset:**
   `C:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Microsoft\VC\v170\Platforms\ARM64\PlatformToolsets\WindowsKernelModeDriver10.0\Toolset.targets`
2. **VS Extension/Project Templates:**
   `C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\Extensions\Microsoft\Windows Driver Kit\wdk.pkgdef`

### Q2: Direct cl.exe / link.exe for ARM64 KMDF (WDK 10.0.26100)

Assuming you are using the VS2022 `Hostx64\arm64` cross-compiler and WDF version `1.33` (adjust `1.33` to your target if needed).

**1. cl.exe (Compile)**
```cmd
cl.exe /c /O2 /kernel /GS /W4 /WX ^
  /D_ARM64_ /DARM64 /D_WIN64 /DNDEBUG /D_KERNEL_MODE ^
  /DKMDF_VERSION_MAJOR=1 /DKMDF_VERSION_MINOR=33 ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\wdf\kmdf\1.33" ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\km\crt" ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\km" ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\shared" ^
  main.c
```
*Note: Do NOT define `AMD64`. `_ARM64_`, `ARM64`, and `_WIN64` are the correct architecture defines.*

**2. link.exe (Link)**
```cmd
link.exe /DRIVER /SUBSYSTEM:NATIVE,10.0 /MACHINE:ARM64 /NODEFAULTLIB /INTEGRITYCHECK ^
  /ENTRY:"FxDriverEntry" ^
  /LIBPATH:"C:\Program Files (x86)\Windows Kits\10\Lib\10.0.26100.0\km\arm64" ^
  /LIBPATH:"C:\Program Files (x86)\Windows Kits\10\Lib\wdf\kmdf\arm64\1.33" ^
  BufferOverflowFastFailK.lib ntoskrnl.lib hal.lib wdfldr.lib wdfdriverentry.lib ^
  /OUT:mydriver.sys main.obj
```

**KMDF Entry Point & Version Binding:**
*   **Linker Entry Point:** You specify `/ENTRY:"FxDriverEntry"`.
*   **How it works:** `FxDriverEntry` is compiled into `wdfdriverentry.lib`. When the OS loads your driver, it calls `FxDriverEntry`. This stub reads the `KMDF_VERSION_MAJOR` and `MINOR` defines baked into your compiled binary, binds your driver dynamically to the WDF runtime (via `wdfldr.lib`), initializes the `/GS` security cookie, and **then** calls your custom `DriverEntry` function in your C code.

### Q3: KMDF vs plain WDM for Minimal Manually Linked Skeleton

**Recommendation:** For a strictly manually-compiled, minimal skeleton with the fewest dependencies, **plain WDM is highly recommended.**

KMDF requires linking version-specific WDF stub libraries and runtime binders. WDM requires only standard kernel libraries, making the command line significantly simpler and avoiding side-by-side versioning entirely.

**WDM Minimal cl.exe:** (Removed WDF includes and defines)
```cmd
cl.exe /c /O2 /kernel /GS /W4 /WX ^
  /D_ARM64_ /DARM64 /D_WIN64 /DNDEBUG /D_KERNEL_MODE ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\km\crt" ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\km" ^
  /I"C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\shared" ^
  main.c
```

**WDM Minimal link.exe:** (Removed WDF libs, changed Entry Point)
```cmd
link.exe /DRIVER /SUBSYSTEM:NATIVE,10.0 /MACHINE:ARM64 /NODEFAULTLIB /INTEGRITYCHECK ^
  /ENTRY:"GsDriverEntry" ^
  /LIBPATH:"C:\Program Files (x86)\Windows Kits\10\Lib\10.0.26100.0\km\arm64" ^
  BufferOverflowFastFailK.lib ntoskrnl.lib hal.lib ^
  /OUT:mydriver.sys main.obj
```

*Note on WDM Entry:* In WDM, the linker entry point must be `/ENTRY:"GsDriverEntry"`. This is provided by `BufferOverflowFastFailK.lib`. It initializes the `/GS` buffer security cookie for kernel mode and then automatically jumps to your `DriverEntry`.
