## Response

這是一條極具挑戰性但架構上最合理的「正統」路線。將 Linux 的開源驅動資產（Mesa）搬到 Windows WDDM 架構下，核心工作是**抽換底層的作業系統/記憶體管理介面（Winsys）**，並對接 Windows 的 D3D DDI。

以下是針對你提出的 5 個問題，給出的可落地細節與執行步驟：

---

### 1. 在 Windows 上 Build Mesa v3d
要在 Windows ARM64 上把 V3D Gallium driver 編譯出來，並掛上 d3d10umd。

*   **編譯工具鏈**：強烈建議使用 **`clang-cl`** (LLVM for Windows) 而非純 MSVC。Mesa 內部有太多 C99/C11 與 GNU extension，MSVC 支援度較差，`clang-cl` 能偽裝成 MSVC 並完美相容 Windows SDK。
*   **Meson Options**：
    需要下達類似以下的指令：
    ```bash
    meson setup builddir --cross-file=arm64_windows.txt -Dos=windows -Dgallium-drivers=v3d -Dgallium-d3d10umd=true -Dshared-glapi=false -Dllvm=disabled
    ```
    *(註：`gallium-d3d10umd` 在較新的 Mesa 版本中可能改名或整併入 `gallium-windows` 或由特定 target 控制，**[需查 Mesa source: `meson_options.txt`]**)*。
*   **會卡在哪（Roadblocks）**：
    1.  **`libdrm` 依賴**：V3D driver 預期底層有 `xf86drm.h` 和 `v3d_drm.h`。在 Windows 上沒有這些東西。
        *   *解法*：你需要寫一個假的 (stub) `libdrm` header，或者在編譯時將 `v3d_drm.h` (定義 DRM IOCTL struct) 直接複製一份過來給你的 Winsys 參考。
    2.  **POSIX API (OS-Specific)**：Mesa 已經有 `util/os_misc.c` 處理跨平台，但 V3D 驅動內可能偷用 Linux 特有的 API（如 `fd` 檔案描述符操作 `dup()`, `mmap()`）。
        *   *解法*：在 Windows 上，資源控制代碼是 `HANDLE` 而非 `fd`。需要將 V3D 程式碼中傳遞 DRM fd 的邏輯，替換成傳遞 WDDM `D3DKMT_HANDLE` 或自訂的 Handle。
    3.  **V3D Simulator**：Mesa v3d 內建一個能在 CPU 上跑的 Simulator (基於 v3d_simulator.c)，它依賴 Linux API。編譯時確保 `-Dv3d-simulator=disabled`。

---

### 2. Winsys 介面（最關鍵：Linux DRM vs. Windows WDDM）
Mesa 內部架構是 `Gallium State Tracker -> V3D Screen/Context -> Winsys -> Kernel`。你需要新增一個資料夾 `src/gallium/winsys/v3d/win/`，實作一個 Windows 版的 Winsys。

對照 `v3d_drm_winsys.c`，你需要向上層 Gallium (如 `v3d_screen.c`) 提供以下核心介面（定義在 `v3d_winsys.h`）：

#### A. 必須實作的介面與 WDDM (D3DKMT) 的對應
1.  **`v3d_winsys_alloc_bo(..., size, name)`**
    *   *Windows 實作*：呼叫 `D3DKMTCreateAllocation`。準備 `D3DDDI_ALLOCATIONINFO`，將 V3D 需要的記憶體大小與屬性（如是否可 cache）打包傳給 KMD。KMD 會配發實體記憶體並返回 `hAllocation` (對應 Linux 的 `bo->handle`)。
2.  **`v3d_winsys_bo_map(...)`**
    *   *Windows 實作*：呼叫 `D3DKMTLock2` 或 `D3DKMTMapGpuVirtualAddress`。向 WDDM 請求將 GPU 記憶體映射到 CPU User-mode virtual address，讓 Mesa 可以寫入 Uniforms 或 Command (CL)。
3.  **`v3d_winsys_submit_cl(...)` 或類似的 Job Submit**
    *   *Windows 實作*：呼叫 `D3DKMTSubmitCommand` 或 `D3DKMTRender`。將建立好的 Control List (Binner / Render CL) 的 GPU 虛擬位址與長度，封裝在私人驅動資料 (Private Driver Data) 中丟給 KMD。
4.  **`v3d_winsys_bo_wait(...)` (Fence/Wait)**
    *   *Windows 實作*：WDDM 使用 Monitored Fence。當 Submit CL 時，給予一個 Fence Value。Wait 時呼叫 `D3DKMTWaitForSynchronizationObjectFromCpu`，阻塞 User-mode 直到 GPU 跑完。
5.  **`v3d_winsys_get_param(...)`**
    *   *Windows 實作*：呼叫 `D3DKMTEscape` (後門) 向 KMD 查詢。例如查詢硬體是 V3D 版本幾（Pi 5 是 V3D 7.1）、有多少 QPU cores、記憶體大小等。

#### B. Kernel Mode Driver (KMD) 的對應操作
Linux DRM IOCTL 在你未來的 WDDM KMD 中，會變成 `DxgkDdi` 回呼函式：
*   `DRM_IOCTL_V3D_CREATE_BO` -> **`DxgkDdiCreateAllocation`**：在 Kernel 設定分頁表 (GART/MMU)。
*   `DRM_IOCTL_V3D_SUBMIT_CL` -> **`DxgkDdiSubmitCommand`**：KMD 解析 User-mode 送來的 CL，執行安全驗證 (Validation)，然後寫入 V3D 的 Hardware Registers (如 `V3D_CLE_BFC` / `V3D_CLE_RFC`) 來觸發執行。
*   `DRM_IOCTL_V3D_WAIT_BO` -> 依賴 WDDM 的 **Fence 機制**與 **`DxgkDdiInterruptRoutine`** (硬體中斷處理)。

---

### 3. d3d10umd State Tracker
`d3d10umd` 是 Mesa 將 Gallium 驅動包裝成 Windows User-Mode Driver 的介面層。
*   **運作原理**：Windows 的 DirectX Runtime (`d3d11.dll`) 會尋找並載入你的 UMD DLL。Mesa 的 `d3d10umd` 會實作 `OpenAdapter10_2`、`CreateDevice` 等 DDI (Device Driver Interface)，並把它們轉換成 Gallium 的 `pipe_context` 呼叫 (如 `draw_vbo`, `set_constant_buffer`)。
*   **需要 KMD 提供什麼**：UMD 初始化時，DX Runtime 會傳入一個 `KTCallbacks` 結構，裡面包含 `pfnAllocateCb`, `pfnEscapeCb`, `pfnRenderCb` 等指向 `gdi32.dll/dxgikernel` 的函數指標。UMD 必須透過這些 Callback 才能跟 KMD 溝通。你的 Winsys 需要攔截/使用這些 Callback，而不是自己去 LoadLibrary 叫 `D3DKMT*`。
*   **DWM 的需求**：Windows 10/11 的 DWM 預設要求 **D3D11 Feature Level 11_0 或至少 10_0**。Mesa 的 `d3d10umd` 實際上**支援 D3D11 DDI**。只要你的 V3D Gallium 驅動能滿足 D3D11 的功能要求（Pi5 V3D 7.1 支援 Vulkan 1.2 / GLES 3.1，硬體能力足以對應 Feature Level 11_0），`d3d10umd` 是足夠讓 DWM 跑起來的。**[需實機驗證 DWM 是否對特定 format 支援有硬性要求]**。

### 4. Phase 2 獨立驗證（不掛 WDDM DWM 的極簡路線）
這是一條極度推薦的「保命路線」。WDDM 規定太繁瑣，一開始直接寫 Dxgkrnl miniport 絕對會 BSOD 到崩潰。

*   **極簡 KMD 怎麼弄**：
    寫一個標準的 **KMDF (Kernel-Mode Driver Framework)** 驅動（非 Display Miniport），建立一個 Device Object `\\.\V3D_Pi5`。
    實作 `EvtIoDeviceControl`，自訂幾個簡單的 IOCTL：
    *   `IOCTL_V3D_ALLOC_MEM`
    *   `IOCTL_V3D_MAP_MEM`
    *   `IOCTL_V3D_SUBMIT_CL`
    *   `IOCTL_V3D_WAIT_IDLE`
*   **改 Mesa Winsys**：
    你的 `v3d_win_winsys` 不要呼叫 `D3DKMT*`，而是用標準 Windows API：
    `HANDLE hDev = CreateFile("\\\\.\\V3D_Pi5", ...);`
    然後用 `DeviceIoControl(hDev, IOCTL_V3D_SUBMIT_CL, ...)` 來丟 Command。
*   **跟完整 WDDM KMD 差在哪**：
    極簡 KMD **不歸 `Dxgkrnl.sys` 管**。沒有 D3D 記憶體管理 (VidMm)、沒有 GPU 排程器 (VidSch)。你需要自己寫程式把實體記憶體對應到 GPU 的 MMU，自己寫暫存器控制。你不能把它註冊成 Display Miniport。
*   **第一個「GPU 真的有跑」的驗收點 (Milestone 1)**：
    **不要一開始就跑 Shader！**
    1.  *Target*: **Clear a Buffer via Hardware**。
    2.  準備一塊記憶體 (Buffer)。
    3.  手刻一條最短的 Control List (CL)：設定 Tile Binning，使用 V3D 的硬體 Clear 指令 (把 Buffer 填滿 `0xDEADBEEF` 紅色)。
    4.  Submit CL，等待硬體中斷 (或迴圈 Polling 暫存器狀態)。
    5.  用 CPU 讀取該 Buffer，看是不是變紅了。
    *(成功做到這點，代表你的 PCI/SoC 暫存器映射、GPU MMU 分頁表、中斷、Clock/Power 都通了，這是最難的一步)*。

---

### 5. Shader 編譯路線 (D3D -> NIR -> V3D QPU)
在 d3d10umd 路線中，Mesa 內部的 Shader 轉換鏈是這樣走的：

1.  **DirectX 應用 (DWM/Game)**：提供 HLSL 並編譯成 **DXBC** bytecode。
2.  **Mesa d3d10umd**：接收 DXBC，Mesa 的 `src/gallium/frontends/d3d10umd` 會將 DXBC 解析，轉換成 Gallium 的共通表示法 **TGSI** (或現在更新的 **NIR**)。
3.  **V3D Gallium Driver**：
    *   接收到 TGSI 或 NIR。V3D 驅動現在全面採用 **NIR**。
    *   如果是 TGSI，會經過 `tgsi_to_nir` 轉換。
    *   接著進入 V3D 專屬編譯器 (`src/broadcom/compiler/v3d_compiler.c`)。
    *   NIR 會被優化，最後轉成 **V3D QPU Assembly**（Broadcom 專屬硬體指令）。
4.  **上傳**：QPU Assembly 作為 Binary 塞進 Shader Buffer 透過 CL 丟給 GPU。

**在 Windows 上的支援度**：
*   **DXBC -> TGSI/NIR**：這條路徑在 Mesa 內部非常成熟（多虧了 Linux 上的 Nine、Gallium 等專案）。
*   **TGSI/NIR -> V3D QPU**：只要你在 Windows 上能成功編譯 Broadcom compiler (`v3d_compiler.c` 及其依賴的 `nir` 模組)，轉換過程是**純 CPU 計算，與 OS 完全無關**。
*   **潛在坑點**：V3D 編譯器非常吃重 NIR 優化路徑。在 Windows MSVC/clang-cl 下如果編譯器最佳化導致浮點數行為異常，可能會產出壞掉的 QPU 程式碼。**[需查 Mesa source：確保編譯器開關 `-fno-math-errno`, `-fno-strict-aliasing` 等有正確透傳到 Windows build]**。
