========================================================================
Windows-on-ARM (ARM64) driver architecture question. Hardware: Raspberry Pi 5. The BCM2712 SoC has a PCIe root complex; a multi-function I/O chip "RP1" hangs off PCIe. RP1's internal peripherals (6x PL011-ish UART, 7x DesignWare I2C, 8x DW SPI, GPIO/pinctrl, Cadence GbE, 2x DWC3 USB, PWM, I2S) are NOT standard PCI functions/BARs - they live at fixed offsets inside RP1's single PCIe BAR (Linux describes them via a Device Tree overlay attached to the PCI device). RP1 also has its own internal interrupt controller that funnels IRQs out via PCIe MSI-X to the GIC.

I need to make these peripherals enumerable on Windows so per-peripheral class drivers (SerCx2/SpbCx/GpioClx/NDIS/USB) can bind. Questions:

1. Recommended architecture: (A) describe each RP1 sub-peripheral as an ACPI device (_HID + _CRS memory at the CPU-visible PCIe-mapped address) directly in DSDT under the PCIe device, vs (B) a custom KMDF "RP1 bus driver" that binds to the RP1 PCI function, maps the BAR, and dynamically enumerates child PDOs handing each its MMIO sub-window + interrupt. Trade-offs on Windows-on-ARM specifically.

2. The hard part: RP1's internal interrupt controller / MSI-X demux. How is a PCIe device's internal interrupt controller (that multiplexes ~many peripheral IRQs onto MSI-X vectors) best represented on Windows so child devices get line-based interrupts? Can ACPI express this, or does it require the bus driver to own the MSI-X and re-dispatch (a custom interrupt mux)?

3. Does the BCM2712 PCIe root complex need a custom Windows driver, or can UEFI firmware expose a standard ECAM host bridge (ACPI PNP0A08) so inbox pci.sys handles it? What must firmware do (outbound/inbound windows, link training) vs the OS?

4. For the ACPI route: minimal DSDT/ASL skeleton shape for one RP1 peripheral child (e.g. a UART) - _HID, _CRS (QWordMemory within RP1 BAR + interrupt), _DSD if needed. And which ASL compiler ships in WDK 10.0.26100 (asl.exe path?).

Be architecture-focused and accurate for Windows-on-ARM. This is the foundational "make RP1 visible" track.

RESPONSE
========================================================================
This is a classic Windows-on-ARM (WoA) enablement challenge. Translating Linux's flexible Device Tree (DT) `simple-bus` topologies into the rigid, standardized ACPI/PNP architecture of Windows requires specific design patterns. 

Here is the architectural blueprint for exposing the Raspberry Pi 5’s RP1 silicon to Windows standard class drivers.

---

### 1. Recommended Architecture: The KMDF "Resource Hub" Bus Driver
**Recommendation: (B) A custom KMDF Bus Driver for RP1.**

**Why (A) pure ACPI fails on Windows:**
Linux allows a DT overlay to describe static memory offsets inside a dynamically assigned PCI BAR. Windows `pci.sys` and `acpi.sys` do not support this natively. If you simply put child devices in the DSDT under the PCI device, Windows will evaluate their namespace, but it **will not** automatically instantiate PDOs (devnodes) for them, nor will it dynamically patch their `_CRS` memory boundaries based on where `pci.sys` placed the BAR.

**The Windows-on-ARM Pattern:**
1. **Match the PCI Function:** Write a KMDF driver (e.g., `rp1bus.sys`) that binds to the RP1's PCI Vendor/Device ID.
2. **Claim the BAR:** In `EvtDevicePrepareHardware`, `rp1bus.sys` receives the base physical address of the RP1 BAR.
3. **Dynamic Enumeration:** The bus driver uses `WdfChildListAddOrUpdateChildDescriptionAsPresent` to dynamically create Child PDOs for the UARTs, I2C, SPI, etc.
4. **Resource Slicing:** During PDO creation (`EvtChildListCreateDevice`), the bus driver creates secondary `WDFCMRESLIST` resource lists. It slices the parent BAR into smaller `CmResourceTypeMemory` chunks (using the known RP1 internal offsets) and hands them to the specific children.
5. **ACPI Binding:** You call `WdfPdoInitAssignAcpiName` when creating the child PDO. This tells the Windows PNP manager to link the dynamically created KMDF PDO with a specific ACPI namespace node in the DSDT, allowing the child to pull down `_DSD` properties (like clock speeds or pinmuxes) and `_CRS` non-memory resources.

### 2. The Hard Part: MSI-X Demux to Line-Based Interrupts
You cannot pass an MSI-X vector directly to standard class drivers (SerCx2, SpbCx) if that vector is shared/multiplexed internally by RP1. Furthermore, Windows KMDF bus drivers cannot easily mint "fake" `CmResourceTypeInterrupt` resources out of thin air.

**The Solution: Expose RP1 as a GpioClx Interrupt Controller.**
This is the standard Windows paradigm for SoC internal interrupt multiplexers.
1. **The Role of `rp1bus.sys`:** Alongside being a bus enumerator, your driver registers as a GPIO Controller using the inbox **`GpioClx`** framework.
2. **MSI-X Ownership:** `rp1bus.sys` claims the PCIe MSI-X vectors. It owns the ISR.
3. **Interrupt Muxing:** When the MSI-X fires, `rp1bus.sys` reads the RP1 internal interrupt status registers. It then calls into `GpioClx` to signal that a specific "GPIO Pin" (which actually represents an internal RP1 peripheral IRQ line) has fired.
4. **Child ACPI Setup:** In the ACPI DSDT, you give the child UART/I2C device a **`GpioInt`** resource pointing to the RP1 node, rather than a standard `Interrupt`. 
5. **The Magic:** Standard Windows class drivers (like standard DWC3, SerCx2, and NDIS) natively understand `GpioInt` resources. The Windows kernel seamlessly translates the ACPI `GpioInt` into a standard `CmResourceTypeInterrupt` during the child's `EvtDevicePrepareHardware`. The child driver operates entirely unaware that its interrupt is being multiplexed over an MSI-X vector.

### 3. BCM2712 PCIe Root Complex: Firmware vs. OS
You **do not** want to write a custom PCIe host bridge driver. Windows `pci.sys` is massive, complex, and assumes a standard ACPI PCI architecture. 

**Recommendation:** Expose a standard ECAM host bridge (`PNP0A08`) via ACPI. Let inbox `pci.sys` handle it.

**Firmware (UEFI/EDK2) Responsibilities:**
Because Windows on ARM expects ServerReady/SystemReady compliance, the UEFI *must* do the heavy lifting before `winload.efi` executes:
* Initialize the BCM2712 PCIe PHY and assert PERST#.
* Perform Link Training with the RP1.
* Assign the primary Bus numbers.
* Program the BCM2712 Root Port's inbound (DMA) and outbound (MMIO) window translation registers.
* Expose the standard **MCFG** ACPI table (pointing to the PCIe ECAM base address).

**OS/ACPI Responsibilities:**
The ACPI DSDT will contain the `PNP0A08` node. Its `_CRS` will define the `WordBusNumber` and the `DWordMemory` / `QWordMemory` (the aperture Windows is allowed to use for BAR allocation). `pci.sys` will read the MCFG, parse the `_CRS`, enumerate RP1 via ECAM config space, and assign the BAR.

*Note: If the BCM2712 requires proprietary PHY power management during OS runtime (D0-D3 transitions), you handle this by writing a Platform Extension Plug-in (PEP) driver, not a custom PCI driver.*

### 4. ACPI DSDT Skeleton & ASL Compiler
Even though `rp1bus.sys` creates the PDO, ACPI is required for the `GpioInt` wiring and device-specific properties. 

**ASL Compiler Location:**
In WDK 10.0.26100, the Microsoft ASL compiler is located at:
`C:\Program Files (x86)\Windows Kits\10\Tools\10.0.26100.0\x64\asl.exe`
*(Note: Many WoA developers prefer using `iasl.exe` from the open-source ACPICA project, as Microsoft's internal compiler can be overly pedantic or lag behind newer ACPI specifications).*

**Minimal DSDT Skeleton:**
Here is how you bridge the PCI device, the KMDF Bus Driver, and a child UART.

```asl
// The BCM2712 PCIe Root Complex
Device (PCI0) {
    Name (_HID, EisaId("PNP0A08"))
    Name (_CID, EisaId("PNP0A03"))
    // ... _CRS with Bus Numbers and Memory Apertures ...

    // The RP1 Multi-Function Device (PCI Endpoint)
    Device (RP1) {
        // _ADR binds this ACPI node to PCI Device 1, Function 0
        Name (_ADR, 0x00010000) 
        
        // rp1bus.sys must call WdfPdoInitAssignAcpiName(&Init, &"URT0") 
        // to link the PDO to this specific child node.
        Device (URT0) {
            // Standard ARM PL011 UART identifier used by Windows SerCx2
            Name (_HID, "ARMH0011") 
            Name (_UID, 0)

            Method (_CRS, 0, NotSerialized) {
                Name (RBUF, ResourceTemplate () {
                    // DO NOT put memory here. The KMDF rp1bus.sys will 
                    // dynamically generate the CmResourceTypeMemory 
                    // by slicing the BAR and giving it to this PDO.

                    // RP1 Muxed Interrupt mapped as a GpioInt.
                    // "RP1" points to the parent which acts as the GpioClx controller.
                    // Pin 14 is the logical RP1 internal interrupt for UART0.
                    GpioInt (Level, ActiveHigh, Exclusive, PullNone, 0, "\\_SB.PCI0.RP1") { 14 }
                })
                Return (RBUF)
            }

            // Optional Device Properties (e.g., UART clock speed)
            Name (_DSD, Package () {
                ToUUID("daffd814-6eba-4d8c-8a91-bc9bbf4aa301"),
                Package () {
                    Package () { "clock-frequency", 48000000 }
                }
            })
        }
        
        // Example: I2C Controller
        Device (I2C0) {
            Name (_HID, "BCM2841") // Assuming DesignWare standard ID
            // ... Similar _CRS with GpioInt ...
        }
    }
}
```

### Summary of the Execution Flow
1. Windows boots. `pci.sys` reads standard ECAM/ACPI and sees the RP1 endpoint.
2. `pci.sys` reads the RP1 config space, assigns a physical address to the RP1 BAR.
3. Windows loads your `rp1bus.sys` on the RP1 PCI node.
4. `rp1bus.sys` registers as a `GpioClx` interrupt controller and hooks the MSI-X vector.
5. `rp1bus.sys` calls `WdfChildListAddOrUpdateChildDescriptionAsPresent` for `URT0`.
6. During PDO creation, `rp1bus.sys` slices off `0x1000` bytes of the BAR (at the UART offset) and assigns it to the child PDO, while calling `WdfPdoInitAssignAcpiName` to link it to the ACPI node.
7. Windows PNP manager sees the new PDO, sees the `ARMH0011` hardware ID, and loads the standard inbox UART class driver.
8. The UART driver asks for its resources. Windows PNP seamlessly merges the MMIO slice from the bus driver with the `GpioInt` from ACPI into a standard resource list. The UART driver binds successfully.
