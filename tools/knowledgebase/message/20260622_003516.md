## Response

這是一項極具挑戰性且非常硬核的系統工程。承接你的架構（Pi5 BCM2712 `rpivid` -> KMDF -> User-mode MFT），以下為可落地的實作細節。

**聲明**：Broadcom 從未公開 `rpivid` 的暫存器手冊。以下硬體行為（Fact）均基於對 Linux 核心源碼 (`drivers/staging/media/rpi/rpivid/`) 的逆向與理解；Windows 實作細節（Deduction/Design）則基於標準 WDF 驅動開發架構。

---

### 1. rpivid KMDF Driver 骨架

#### 1.1 MMIO 與 ACPI Resource
*   **Fact (Linux 源碼)**：`rpivid` 在 Device Tree 中通常包含兩個核心區塊：`intc` (Interrupt Controller 特有區塊) 與 `hevc` (HEVC 核心暫存器)，以及一個附屬的 Clock/Reset 控制區。
*   **KMDF 落地做法**：
    *   在 UEFI/ACPI 的 DSDT 表中，需定義一個虛擬裝置（例如 `RPIV0001`），將這幾個記憶體區間（Memory32Fixed）與中斷號（Interrupt）包進去。
    *   在 KMDF 的 `EvtDevicePrepareHardware` 中：
        *   遍歷 `WdfCmResourceList`，找出 `CmResourceTypeMemory`。
        *   使用 `MmMapIoSpaceEx` (設定為 `PAGE_NOCACHE` 或 `PAGE_WRITECOMBINE`) 映射出虛擬位址。
        *   **【需查 Linux rpivid source】**：確切的 MMIO Base Address、HEVC Core Register Offset、INTC Offset。

#### 1.2 Decode 提交模型
*   **Fact**：標準的 Ring Buffer / Descriptor Chain 架構。
*   **流程**：
    1. 將控制結構（Phase 1/2 Command Buffers）與 Slice Data (Bitstream) 的**實體位址 (Physical Address)** 寫入特定的 MMIO 暫存器。
    2. 寫入控制暫存器的 START bit（**【需查 Linux rpivid source】** 確切的 trigger register offset）。
    3. 硬體開始 DMA 讀取 -> 解碼 -> 寫出 SAND 格式圖像 -> 拉高 IRQ 線。

#### 1.3 IRQ 與 User-mode 通知
*   **KMDF 實作**：使用 **Pended IOCTL (Overlapped I/O)** 是最標準且效能最好的做法（類似 Linux 的 `poll`/`eventfd`）。
    *   **ISR (`EvtInterruptIsr`)**：讀取中斷狀態暫存器確認是 Decode Done，寫入 ACK bit 清除中斷（**【需查 Linux rpivid source】** 確切的 IRQ Status/Clear register offset）。然後回傳 `TRUE` 並觸發 DPC。
    *   **DPC (`EvtInterruptDpc`)**：從 WDFQUEUE 中取出 pending 的 IOCTL Request，呼叫 `WdfRequestComplete` 將結果返回給 MFT。

#### 1.4 IOCTL 介面建議
```cpp
// 1. 分配 DMA 記憶體 (Driver 呼叫 WDF DMA Enabler 獲取連續實體記憶體)
#define IOCTL_RPIVID_ALLOC_DMA_BUFFER  CTL_CODE(FILE_DEVICE_UNKNOWN, 0x801, METHOD_BUFFERED, FILE_ANY_ACCESS)

// 2. 提交解碼任務 (帶入 Control Struct, 且此 IOCTL 會被 Pend 住直到 IRQ 觸發才 Complete)
#define IOCTL_RPIVID_SUBMIT_AND_WAIT   CTL_CODE(FILE_DEVICE_UNKNOWN, 0x802, METHOD_BUFFERED, FILE_ANY_ACCESS)

// 資料結構範例
struct RPIVID_SUBMIT_REQ {
    UINT64 bitstream_pa;       // Slice 壓縮資料實體位址
    UINT32 bitstream_size;
    UINT64 config_struct_pa;   // 對應硬體格式的配置結構實體位址
    UINT64 reference_pas[16];  // DPB 參考幀實體位址表
    UINT64 output_pa;          // 輸出緩衝區實體位址
};
```

### 2. Stateless 解碼流程 (V4L2 映射到硬體)

Stateless 的核心精神：**硬體是個瞎子，Host 要餵給它最終嚼碎的指令。**

*   **Fact**：在 Linux 源碼中，V4L2 controls (如 `V4L2_CID_STATELESS_HEVC_SPS`) 會在 driver 內部被重新打包成 `rpivid` 硬體看得懂的 **Hardware Descriptors (Phase 1 / Phase 2 params)**。
*   **KMDF 落地做法**：在 User-mode MFT 中解析 NALU，將參數填好，直接在 User-mode 或 Driver 組裝成硬體需要的 Descriptor 格式，然後傳實體位址給硬體。
*   **映射對應**：
    *   **SPS / PPS** (Pic Width, Height, CTU size, Bit depth)：轉譯為硬體 Descriptor 的 Header 欄位（**【需查 Linux rpivid source】** 搜尋 `rpivid_h265_setup` 或類似函數中的位元遮罩與平移操作，例如 `(width << 16) | height` 等 Register layout）。
    *   **Scaling Lists**：如果影片有自定義 Scaling matrix，需開一塊實體記憶體放進去，並把 PA 寫入 Descriptor 的特定欄位。
    *   **Slice Data**：
        *   **Fact**：硬體通常需要**去除了 Emulation Prevention Bytes** 的原始 RBSP，或者需要帶有 Start Code 的 Annex B 格式。**【需查 Linux rpivid source】** 尋找 `slice_params` 是如何將資料餵給 DMA 的。推測 `rpivid` 可以直接吃包含 Start Code 的連續 NALU stream，硬體內部有 parser 找 start code。

### 3. DPB / Reference Frame 管理

*   **Host 端維護**：User-mode MFT 必須自己寫一個 DPB Manager。每解完一張 Frame，把它放進 DPB list。
*   **RPS (Reference Picture Set) 映射**：
    *   Slice Header 裡面會有 L0 和 L1 的參考幀清單（存的是 POC - Picture Order Count）。
    *   硬體不認識 POC，它只認識 index (0~15)。
    *   **落地做法**：MFT 查找 DPB，找出該 POC 對應的 Frame Buffer **實體位址 (PA)**。將這些 PA 填入上述 `RPIVID_SUBMIT_REQ` 的 `reference_pas[16]` 陣列中。硬體 Descriptor 會有對應的 Reference Address Table。

---

### 4. SAND 輸出格式與轉換

*   **Fact**：`rpivid` 輸出的是 **Broadcom SAND 格式** (Column-based tiled memory)，並非 Linear NV12。這是為了優化 DRAM burst read/write 頻寬。
*   **SAND Layout**：通常是 128-byte 寬的垂直條（Column），Y 平面和 UV 平面分開存放（Macroblock-tiled）。**【需查 Linux rpivid source】** 搜尋 `v4l2_pixel_format` 中的 `V4L2_PIX_FMT_NV12_COL128` 或 `SAND128` 定義。
*   **轉換演算法 (SAND -> Linear NV12)**：
    *   需寫一組 CPU (C/C++ + ARM NEON 組合語言) 函數，按照 Column 寬度去定址，將 Tile 記憶體搬移成逐行的 Linear NV12。
*   **ISP 硬體加速可行性**：
    *   在 Linux 上，這確實是交給 Pi 的 ISP (Image Signal Processor) 去把 SAND 轉成 NV12/RGB。
    *   **Windows 上的困境**：Windows **沒有** Pi5 ISP 的 KMDF 驅動。如果你要用 ISP 轉，你必須**再寫一個 ISP 的 KMDF 驅動**。
    *   **結論**：早期落地**強烈建議先用 CPU NEON 軟轉**。儘管 4K 下 CPU 負載極高，但這是打通 Pipeline 的唯一捷徑。未來可考慮用 GPU Compute Shader (DirectX 12) 去讀取 SAND 實體記憶體做 Detile，但這需要 WDDM 的支援。

---

### 5. 記憶體管理 (CMA 在 Windows 的等價物)

*   **硬體需求**：所有的 Buffer (Bitstream, Reference frames, Output SAND frames, Hardware Descriptors) 都必須是**連續實體記憶體 (Contiguous Physical Memory)**。
*   **Windows 落地機制**：
    *   不建議直接用 `MmAllocateContiguousMemory`，因為在系統運行一段時間後，記憶體碎片化會導致 4K 所需的大塊連續記憶體分配失敗。
    *   **最佳實踐**：在 Driver 的 `EvtDriverDeviceAdd` 階段，初始化 `WdfDmaEnabler` (設定為 System DMA 或 Packet Based DMA)。使用 `WdfCommonBufferCreate` 來預先分配一塊大記憶體池（類似 Linux 的 CMA - Contiguous Memory Allocator）。
*   **4Kp60 容量估算**：
    *   1 張 4K NV12 (8-bit) = 3840 * 2160 * 1.5 = 12.4 MB。
    *   HEVC 最大 DPB 需要 16 張 = 198 MB。
    *   加上輸出 Queue (約 4 張) 與 Bitstream Buffer。
    *   **結論**：你的 KMDF Driver 初始化時，必須一次性霸佔（Carve out）**至少 256 MB 的 Common Buffer** 供 MFT 自行管理（Allocator）。

### 6. 第一個里程碑：最小驗證路徑

不要一開始就寫 MFT，先寫一個 Console C++ 程式與 KMDF 溝通。

1.  **Driver 端**：完成 ACPI 解析、MMIO 映射、IRQ 註冊，並寫死一個 IOCTL 接收 `Physical Address`，寫入 MMIO 並觸發 START，收到 IRQ 後 Complete IOCTL。
2.  **App 端 (Console)**：
    *   用 FFmpeg 或事先抽好一幀 HEVC **1080p (先別搞 4K) I-Frame** 的 RAW Bitstream。
    *   人為（或用簡單的 Python 腳本分析 Linux 的 ioctl log）寫死這張 I-Frame 該有的 Phase 1/Phase 2 硬體 Descriptor 內容（包含長寬等設定）。
3.  **執行流程**：
    *   App 呼叫 IOCTL 要一塊 DMA 記憶體。
    *   App 將 I-Frame Bitstream 與寫死的 Descriptor 複製進 DMA 記憶體。
    *   App 呼叫 Submit IOCTL，驅動將 PA 寫入暫存器並啟動。
    *   驅動收到 IRQ，返回 App。
    *   App 從 DMA 記憶體中讀回 Output Buffer (這時是 SAND 格式)。
4.  **驗證**：
    *   寫一個簡單的 C 迴圈（先不管效能），把 SAND 轉成 Linear NV12。
    *   存成 `.yuv` 檔案。
    *   在 PC 上用 YUV Player (如 YUVeye) 打開，看是否出現清晰的畫面（哪怕只有亮度 Y 正確也是巨大成功）。

這條路極度艱辛，核心工作量有 60% 在於**對照 Linux 驅動源碼，還原出那些沒有說明的 MMIO Register Offset 和 Descriptor Bitmask**。祝你好運！
