## Response

這是一個非常硬核且極具挑戰性的專案！將 Pi5 的 HEVC 硬解透過 KMDF 帶到 Windows on ARM，並包裝成 MFT，是打通生態系的重要一步。

針對你的問題，以下是具體的實作細節、API 流程與**最殘酷但真實的落地評估**。

---

### 1. IMFTransform 實作 (最小可行 MFT)

要讓 Media Foundation (MF) 認可你的 MFT，必須實作 `IMFTransform` 介面。建議實作成 **Sync MFT (同步 MFT)**，因為 Async MFT 規範極度繁瑣且容易與第三方 Splitter 不相容。

*   **核心必須實作的方法**：
    *   `GetStreamLimits`, `GetStreamCount`：回傳 1 input, 1 output。
    *   `GetInputAvailableType`：暴露你支援的輸入 (回傳 `MFVideoFormat_HEVC`)。
    *   `GetOutputAvailableType`：暴露你的輸出 (回傳 `MFVideoFormat_NV12`)。
    *   `SetInputType` / `SetOutputType`：系統選定格式後會 call 這裡，你要在這裡初始化 KMDF session。
    *   `GetInputStreamInfo` / `GetOutputStreamInfo`：宣告你需要的 buffer 大小與 alignment。
    *   `ProcessMessage`：處理 `MFT_MESSAGE_COMMAND_FLUSH` (Seek 時清空 DPB) 和 `MFT_MESSAGE_NOTIFY_BEGIN_STREAMING` 等狀態。
    *   `ProcessInput`：收壓縮資料。
    *   `ProcessOutput`：吐解碼後的 NV12。

*   **Type 怎麼設**：
    *   Input: 建立一個 `IMFMediaType`，設定 `MF_MT_MAJOR_TYPE` = `MFMediaType_Video`, `MF_MT_SUBTYPE` = `MFVideoFormat_HEVC`。*(注意：Windows 預設 HEVC 有兩種 bitstream 格式：Annex B (Start codes) 或 HEVC (MP4 length-prefixed)。你必須在 `SetInputType` 檢查並決定你的 KMDF 吃哪種。)*
    *   Output: `MF_MT_MAJOR_TYPE` = `MFMediaType_Video`, `MF_MT_SUBTYPE` = `MFVideoFormat_NV12`，並根據輸入解析出的 SPS/PPS 設定 `MF_MT_FRAME_SIZE` (解析度)。

*   **ProcessInput / ProcessOutput 流程與 DPB 重排**：
    這是一個典型的「非 1-to-1」轉換過程（因為有 B-frame 和 DPB reordering）。
    1.  **ProcessInput**：收到一個 `IMFSample` (HEVC 壓縮檔)，抽出 buffer，透過 `DeviceIoControl` 餵給 KMDF。此時可能還無法輸出畫面。
    2.  **ProcessOutput**：去問 KMDF「有沒有已經解好且排好序的畫面？」。
        *   如果有：把 SAND 轉成 NV12，塞進 `pOutputSamples`，回傳 `S_OK`。
        *   如果沒有 (例如 DPB 還沒滿，需要更多 input)：**回傳 `MF_E_TRANSFORM_NEED_MORE_INPUT`**。這非常重要，這會告訴上游「請再呼叫 ProcessInput 餵我資料」。
    *   **DPB/Reordering 在哪做？**
        *   **最佳解**：Pi5 的 VPU Firmware 通常會自己管理 DPB，並按照 POC (Picture Order Count) 順序吐出解碼好的 Frame。如果是這樣，MFT 只要無腦 Poll KMDF 即可。
        *   **最壞解**：如果 Firmware 只按 Decode Order 吐出，你必須在 **MFT 內部 (User-mode)** 維護一個 DPB 陣列，解析 Slice Header 算出 POC，等 B-frame 到齊後再按照 POC 順序從 `ProcessOutput` 吐出。

### 2. 註冊成系統 HEVC 硬解 MFT

*   **註冊 API**：
    使用 `MFTRegister` (全域註冊，寫入 Registry)。
    Category 使用 `MFT_CATEGORY_VIDEO_DECODER`。

*   **偽硬體 MFT 的 Flags 陷阱**：
    *   **絕對不要用 `MFT_ENUM_FLAG_HARDWARE`**。在 Windows MF 架構下，宣告硬體 MFT 代表你是一個 Async MFT，且必須與 PnP 裝置綁定，更致命的是它預期你會直接輸出 D3D Surface (Zero-copy)。因為你沒有完整的 WDDM (GPU 驅動) 架構，宣告這個會導致系統各種 Crash 或被忽略。
    *   **正確做法**：使用 `MFT_ENUM_FLAG_SYNCMFT`，把自己偽裝成一個**「超高效的軟體 Decoder」**。
    *   在 Windows 的眼中你是 Software Decoder，但實際上你的 MFT 內部透過 KMDF 呼叫了 Pi5 的硬體 VPU。這叫 "System-memory based HW-accelerated MFT"。

*   **Merit (優先權)**：
    Windows 10/11 的 Inbox 播放器預設會抓微軟官方的「HEVC 視訊延伸模組」。要讓系統優先選你，你可以嘗試拉高 Merit (雖然現在微軟對 Merit 控管很嚴格)。最直接的測試方法是**解除安裝微軟的 HEVC 延伸模組**，系統就只剩你的 MFT 可以選了。

### 3. 整合現實 (最殘酷的評估)

這部分是決定專案價值的關鍵。你必須釐清 **MFT** 與 **DXVA (DirectX Video Acceleration)** 的差別。

*   **(A) Windows「電影與電視」/ Media Player / UWP Apps**
    *   **會不會用？** **會**。這些原生微軟 App 走純 Media Foundation 路線。只要你的 MFT 註冊成功，且能吐出標準的 NV12 `IMFSample`，MF 的 Topology Builder 就會把你接上 EVR (Enhanced Video Renderer)。
    *   **效能代價**：因為你吐的是 System Memory (NV12)，EVR 必須用 CPU 把你的 NV12 upload 到 GPU (D3D Texture) 才能畫到螢幕上。對於 4K 影片，這個 Memory Copy 會有一定的 CPU 負載，但 Pi5 的 CPU 應該扛得住。

*   **(B) Edge / Chromium (YouTube 等瀏覽器播放)**
    *   **會不會用？** **絕對不會**。
    *   **原因**：Chromium 為了極致效能，在 Windows 上完全**繞過 MFT**，直接透過 D3D11 去 Query GPU 驅動 (WDDM) 是否支援 `D3D11_VIDEO_DECODE_PROFILE_HEVC_MAIN` (這也就是 DXVA)。因為你沒有 WDDM Render Driver，也沒有 D3D11VideoDevice，Chromium 根本不知道你有硬解能力。
    *   **能不能 Fake (用 WARP 等)？** 很難。WARP (軟體 D3D) 不支援 Video Decode profile。`MF_SA_D3D11_AWARE` 只是告訴 MF 你的 MFT 可以吃/吐 D3D Surface，但前提是你也要有一個 D3D Device 可以建立 Surface。這條路對「瀏覽器硬解」基本上是死胡同，除非你去改 Chromium 的 Source Code (讓它支援 V4L2 或你的 KMDF API)。

*   **(C) 第三方播放器 (VLC / MPC-HC / Kodi)**
    *   **會不會用？** **預設不會**。
    *   **原因**：這些開源播放器核心都是 **FFmpeg**。FFmpeg 在 Windows 找硬解的順序是 DXVA2 -> D3D11VA -> Vulkan Video。它們**不吃 Media Foundation Transform**。如果 DXVA 失敗，它們會 fallback 到 FFmpeg 自己的軟解 (CPU)。
    *   **解法**：MPC-HC (搭配 LAV Filters) 裡面有一個選項叫 "Media Foundation (MF)"，但通常很少人開。若要讓 VLC 支援，正規做法是寫一個 FFmpeg 的 hwaccel 模組去接你的 KMDF，而不是寫 MFT。

**總結這個 Reality Check**：
你寫的 MFT，受眾是 **Windows 原生播放器 (Movies & TV)、Windows Media Player、TopoEdit，以及呼叫 `IMFMediaEngine` 的 Win32/UWP 遊戲或程式**。
無法惠及 Chrome 與 VLC。

### 4. SAND → NV12 放哪？

*   **位置**：必須放在 MFT 的 `ProcessOutput` 裡面。
*   **做法**：
    1. KMDF 解完後，MFT 透過 `mmap` 或 `DeviceIoControl` 拿到一塊裝滿 SAND 格式的 system memory buffer。
    2. 呼叫你寫好的 **ARM64 NEON 組語/Intrinsic 函數**，把 SAND detile 成 linear NV12。
    3. 把 linear NV12 複製到 MF 提供的 `pOutputSamples` 中。
*   **下游反應**：下游的 Renderer (EVR) 收到這個標準 NV12 後，就會當作一般影片資料，自動做 YUV2RGB 跟繪製。它完全不知道（也不用知道）這原本是 SAND 格式。

---

### 5. 誠實結論 + 落地里程碑

**誠實結論**：
這是一條「能讓 Pi5 在 Windows 上用原生播放器看 4K HEVC」的英雄之路。雖然無法讓 Chrome 享有 YouTube 硬解 (這是架構死穴)，但作為一個 System-level 的 PoC，技術含量極高，且能證明 Pi5 VPU 在 Windows 上的可用性。

**實作里程碑 (Milestones)**，強烈建議照這個順序做，不要越級打怪：

*   **Milestone 1: 脫離 MF 的純 C++ Console App**
    *   目標：讀取本機 `test.h265`，餵給 KMDF，拉出 SAND，用 C/C++ 轉成 linear NV12，存成 `out.yuv`。
    *   意義：驗證 KMDF 穩定度、DPB reordering 邏輯、SAND2NV12 的正確性。這步沒通，寫 MFT 只會死在黑畫面，根本無法 debug。
*   **Milestone 2: 實作 NEON 加速的 SAND -> NV12**
    *   目標：在 Console App 裡，確定轉檔 4K 畫面不到 5~10ms。如果用純 C 寫，CPU 會滿載，後續播放會卡頓掉幀。
*   **Milestone 3: 實作 Sync MFT + TopoEdit 測試**
    *   目標：寫好 `IMFTransform`，編譯成 `.dll`，用 `regsvr32` 或 `MFTRegister` 註冊。
    *   測試工具：打開 Windows SDK 附帶的 **TopoEdit**，手動拉線：File Source -> HEVC Splitter -> 你的 MFT -> EVR。
    *   意義：避開播放器的複雜邏輯，純粹驗證 Media Foundation Pipeline 能不能動。這是最感動的一刻：**你在螢幕上看到硬解畫面了。**
*   **Milestone 4: 征服「電影與電視」**
    *   目標：移除系統內的 HEVC 擴充，點擊一個 `.mp4` 或 `.mkv` (HEVC)，系統自動叫起「電影與電視」並流暢播放。
    *   挑戰：處理 Seek (時間軸跳轉)、Flush (清除 DPB)、以及 MP4 HEVC (HVCC length-prefixed) 與 AnnexB bitstream 的相容性問題。

**下一步建議**：先搞定 Milestone 1。然後去 GitHub 找一個叫 **"WavSink"** 或 **"MFT_Decoder_Template"** 之類的微軟官方範例，把你的 KMDF 呼叫塞進它的 `ProcessInput` / `ProcessOutput` 裡。祝武運昌隆！
