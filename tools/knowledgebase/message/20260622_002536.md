### 【A】WDDM Render Driver (Phase 3) 底層實作藍圖

在 Pi5 (V3D 7.1) 上實作 WDDM 的核心，是將 Windows 的記憶體與排程模型（Dxgkrnl）翻譯成 V3D 的硬體語言。

#### 1. WDDM VidMm (Video Memory Manager) 整合
*   **概念**：Windows 負責分配實體記憶體分頁（Physical Pages），驅動負責把這些分頁塞進 GPU 的 MMU（Memory Management Unit），讓 GPU 能用虛擬位址（GPU VA）存取。
*   **實作流程**：
    *   **`DxgkDdiCreateAllocation`**：當 UMD（User-Mode Driver）要求記憶體時，KMD 描述記憶體大小與對齊要求。對 V3D 來說，通常需要分配出能映射為 4KB 分頁的記憶體。
    *   **`DxgkDdiBuildPagingBuffer`**：這是核心。Dxgkrnl 會傳入 Paging 動作（如 `Transfer`、`Map`、`Unmap`）。
    *   **`DxgkDdiMapGpuVirtualAddress`**（WDDM 2.0+）：Windows 給定一段 GPU VA 和對應的實體分頁陣列。
    *   **V3D 硬體對接**：
        *   V3D 有自己的 MMU（與 ARM Cortex-A76 的 MMU 獨立）。
        *   驅動必須維護 V3D 的 Page Directory (PD) 和 Page Table (PT)。
        *   當 `Map` 發生時，驅動將 Windows 給的實體實體位址（PA）寫入 V3D 的 PT 條目（PTE）中（需加上 V3D 要求的屬性 bit，如可讀/可寫/Cache 策略）。
        *   **TLB Flush**：寫入 PT 後，必須寫入 V3D 的 MMU 控制暫存器（如 `V3D_MMU_CTL` 相關暫存器中的 flush bit），迫使 V3D 放棄舊的位址映射快取。

#### 2. GPU 排程與命令提交
*   **概念**：UMD 已經編譯好 V3D 的 Command List (CL) 與 Shader (QPU 機器碼)，KMD 負責把它們丟給硬體執行。
*   **實作流程**：
    *   **`DxgkDdiCreateContext`**：建立硬體 Context，為這個 Context 分配專屬的 GPU VA 空間（透過切換 MMU 的 Page Directory Base Address）。
    *   **`DxgkDdiSubmitCommand`**：Dxgkrnl 把 UMD 做好的 Command Buffer 交給 KMD。
    *   **V3D CLE (Control List Executor) 觸發**：
        *   V3D 是一個 Tile-Based Deferred Renderer (TBDR)。任務分為 Binner（計算哪些頂點落在哪個 Tile，對應 CT0）和 Render（逐個 Tile 渲染，對應 CT1）。
        *   驅動將 Binner CL 的起始 GPU VA 寫入 `V3D_CLE_CT0CA`（Current Address），將結束位址寫入 `V3D_CLE_CT0EA`（End Address）。
        *   **觸發機制**：一旦寫入 `EA` 暫存器，且 `EA` > `CA`，V3D 的 CLE 就會立刻醒來開始吃 Command。
        *   Render (CT1) 同理，通常由 Binner 結束的中斷或硬體同步機制觸發。
    *   **GPU Hang 偵測**：驅動透過讀取 `V3D_CLE_CT0CA` 是否在一段時間內停滯不前，或者依賴 Windows 提供的 Timeout 機制來判定。

#### 3. TDR (Timeout Detection & Recovery)
*   **`DxgkDdiResetFromTimeout`**：當 Windows 發現 GPU 遲遲沒有回報 Monitored Fence，就會呼叫此函數。
*   **V3D 軟 Reset**：
    *   驅動必須寫入 V3D HUB 區塊的重置暫存器（軟體 Reset bit）。
    *   等待硬體 Reset 完成後，必須**重建 MMU 狀態**、重新載入被打斷的 Context 狀態（雖然通常 TDR 後該 Context 會被標記為 guilty 並砍掉），並將其他無辜的 Context 重新丟入 CLE (`CA` / `EA`) 繼續執行。

#### 4. 中斷處理 (Interrupts)
*   **`DxgkDdiInterruptRoutine` (ISR)**：在 DIRQL 級別執行，必須極快。
    *   讀取 V3D 的中斷狀態暫存器。
    *   如果是 **Binner Done** 或 **Render Done**：清除中斷 Flag，回傳 `TRUE`，並觸發 DPC (Deferred Procedure Call)。
    *   如果是 **MMU Fault**：記錄發生 Fault 的 GPU VA 和原因，通常會觸發 TDR。
*   **DPC Routine**：呼叫 `DxgkCbNotifyInterrupt`，告訴 Windows 哪個 Fence ID 已經完成了。

#### 5. 同步 (Synchronization)
*   **Monitored Fence**：Windows 給定一個 GPU VA 和一個 64-bit 數值。
*   UMD 在產生的 Command List 尾端，會插入 V3D 特定的命令封包（如 `Store Multiple` 或專用同步封包），指示 V3D 在做完所有渲染後，將這個 64-bit 數值寫入該 GPU VA，然後觸發 IRQ。OS 收到中斷後檢查該記憶體位址，確認任務完成。

### 【B】最重要：我的知識邊界與 V3D 的開源真相

在此，我必須誠實地劃清界線。以下是實作上述藍圖時，我們面臨的真實情況：

#### 1. 知識邊界與缺口分類

*   **(a) 廠商鎖死/未公開 (Broadcom NDA / 需要逆向)**
    *   **電源與時脈管理 (Power & Clock Gating)**：V3D 7.1 在 Pi5 上的 DVFS（動態電壓頻率調整）極度依賴 Raspberry Pi 的 Firmware（RP1 晶片與 VideoCore 韌體）。如何在 Windows ARM64 下正確透過 Mailbox 或 SCMI 呼叫韌體調整 GPU 時脈？這部分的 Windows ACPI / PEP (Power Engine Plugin) 綁定細節是**未公開且嚴重缺乏文件的**。
    *   **硬體隱藏 Bug (Erratas)**：每個 GPU 都有硬體 Bug，官方驅動會偷偷在軟體裡 Workaround。如果沒有 Broadcom 內部的 Errata 文件，我們只能在 Windows 上遇到 GPU Hang 時抓瞎。

*   **(b) 我的訓練資料不足 (我知道概念，但無法精準默寫)**
    *   **V3D 7.1 確切的暫存器 Offset**：我非常確定存在 `CLE_CT0CA` 這樣的暫存器，但我**無法憑空準確寫出 V3D 7.1 中它的絕對記憶體偏移量 (Hex Address)**。硬要我寫就是在編造。唯一正確的做法是去查閱 Mesa `v3d_regs.h` 或 Linux Kernel 原始碼。
    *   **Windows ARM64 WDDM 3.x 針對 SoC 的特定 DDI 盲區**：微軟對於 x86 PCIe GPU 的 WDDM 有海量文件，但對於 ARM64 SoC UMA（統一記憶體架構）的 Cache Coherency（快取一致性）處理細節，文件非常稀缺。

*   **(c) 只是工程量大 (資料都有，但要做到死)**
    *   **KMD 的狀態機維護**：把 V3D 的中斷與 CLE 排程完美塞進 WDDM 的 Context 狀態機中。
    *   **WDDM Paging 緩衝區翻譯**：把 Windows 的 Paging 請求翻譯成 V3D MMU 格式，這是純粹的苦力活，沒有秘密，但極容易寫出 Blue Screen。

#### 2. 針對 V3D 7.1：它到底開不開放？
**這是我最有把握的事實：相較於 Mali、Adreno、PowerVR，V3D 是「最適合也最容易」被社群移植到 WDDM 的行動/嵌入式 GPU。**

*   **官方文件的缺失與補償**：Broadcom **並沒有**公開 V3D 7.1 的 PDF 架構手冊（他們只公開過舊版 V3D 2.x/3.x）。**但是**，Broadcom 官方僱用的工程師（如 Igalia 團隊與 Pi 基金會）將**所有硬體細節完全以程式碼形式貢獻在 Mesa 中**。
*   **到底有多少是公開的？**
    *   **暫存器定義**：100% 公開（在 Mesa 的 XML 描述檔與 C header 中）。
    *   **CL 封包格式 (Command Packet)**：100% 公開（Binner, Render, Compute 的封包結構全在 Mesa 裡）。
    *   **QPU ISA (Shader 指令集)**：100% 公開。Mesa 有完整的 Broadcom QPU Compiler。
    *   **MMU 格式**：100% 公開（在 Linux Kernel DRM 驅動裡）。
*   **為什麼比別人好？**
    *   **Mali (ARM)**：ARM 官方極度封閉，社群的 Panfrost 是靠瘋狂逆向工程拼湊出來的。
    *   **Adreno (Qualcomm)**：Freedreno/Turnip 也是逆向出來的。
    *   **V3D**：Mesa 裡的 `v3d` / `v3dv` 驅動就是**官方驅動**。它是原廠支援的，也就是說程式碼裡的邏輯就是最正確的硬體操作指南。

**V3D 真正鎖死的是什麼？**
只有 Firmware 溝通介面與底層電源管理，但這些通常是由 Raspberry Pi 的 Linux BSP 處理，移植到 Windows 上需要對 Pi UEFI 韌體做適配。

### 【C】現實的打擊：小團隊的執行計畫與最大阻礙

如果一個 3~5 人的頂尖駭客團隊想在 Pi5 Windows ARM64 上實現「玩家要的完整 GPU 加速（能打 3D 遊戲）」，這是真實的樣貌：

#### 1. 實際要做什麼 (分兩半)
*   **KMD (Kernel-Mode Driver)**：實作上述【A】的所有 DDI。這大概需要 1 個熟悉 Windows 核心的工程師加上 1 個熟悉 Linux DRM/V3D 的工程師，花費 **6 到 12 個月**能做到能跑的程度。
*   **UMD (User-Mode Driver)**：實作 D3D12/D3D11 介面。這包含將 DirectX 的繪圖指令翻譯成 V3D 的 CL 封包，並將 Shader 轉換。

#### 2. 最大的單一阻礙（真正的地獄）
**「DirectX Shader Compiler (DXIL) 到 V3D QPU ISA 的編譯器後端」**

玩家要打遊戲，遊戲吐出來的是 DirectX 的 Shader（DXBC 或 DXIL）。V3D 硬體只聽得懂 Broadcom 自己的 QPU 機器碼。
在 Linux 上，這件事由 Mesa 解決（將 GLSL/SPIR-V 轉為 NIR，再轉為 QPU）。
在 Windows 上，微軟**沒有**提供這種轉換器。你的團隊必須：
1. 自己寫一個 LLVM Backend，把 DXIL 翻譯成 V3D QPU 機器碼。
2. 或著，寫一個轉譯層，把 DXIL 轉成 SPIR-V，然後**把整個 Mesa 巨大的 Shader 編譯器包進你的 Windows UMD 裡面**（這被稱為 D3D12OnVulkan 或類似架構的變形，也是目前社群最可能走的路）。

這不是一個 GPU 硬體問題，這是一個**編譯器工程問題**。這需要耗費極度龐大的心力。微軟的 D3D12 架構本質上要求驅動開發商投入海量資源寫 UMD 編譯器。

#### 3. 誠實結論：能不能真的做出來？

*   **如果目標是「原生的 D3D12/D3D11 WDDM 完整驅動」**：
    **不能。** 對於小團隊來說，在沒有微軟與 Broadcom 資金支援下，手寫原生 UMD 與 DXIL->QPU 編譯器的工程量大到不切實際（這通常是幾十人團隊好幾年的工作量）。
*   **如果目標是「讓玩家有 GPU 加速可用」（社群實務路線）**：
    **能！而且極度有希望。**
    最可行的技術路線是：
    1. 寫一個精簡的 WDDM KMD（只管記憶體、提交、中斷）。
    2. UMD 部分，**不寫原生 D3D**。直接把 Mesa (Vulkan `v3dv` 和 OpenGL `v3d`) 移植到 Windows 上（Mesa 已經支援 Windows 平台，缺的是對接自製 WDDM KMD 的 Winsys 程式碼）。
    3. 然後利用開源界的萬靈丹：**DXVK / VKD3D**。讓 Windows 遊戲以為自己在跑 D3D，實際上由 DXVK 翻譯成 Vulkan，交給移植到 Windows 的 Mesa 處理，最後透過你的 WDDM KMD 送進 V3D 硬體。

**這就是玩家能得到「完整加速」的唯一且最快途徑。** 硬體細節因為開源所以全亮，缺的只是跨平台的接線工與毅力。
