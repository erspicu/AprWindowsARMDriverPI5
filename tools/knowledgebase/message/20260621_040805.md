Here are the precise details for scaffolding a minimal WDDM Full Render KMD on ARM64 using WDK 10.0.26100 via direct command-line tools.

### 1. DriverEntry Pattern & Version
For a full render KMD, you **must** use `DxgkInitialize`. `DxgkInitializeDisplayOnlyDriver` is exclusively for DODs.

**Pattern:**
```c
NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath) {
    DRIVER_INITIALIZATION_DATA InitData = {0};
    
    // For WDK 10.0.26100 (Windows 11 24H2), this resolves to WDDM 3.2.
    // Ensure NTDDI_VERSION is set to NTDDI_WIN11_GE (0x0A00000F) in your cl.exe flags.
    InitData.Version = DXGKDDI_INTERFACE_VERSION; 
    
    // Populate mandatory DDI callbacks here...

    return DxgkInitialize(DriverObject, RegistryPath, &InitData);
}
```
*Note:* The macro `DXGKDDI_INTERFACE_VERSION` will automatically map to `DXGKDDI_INTERFACE_VERSION_WDDM3_2` (or the highest interface version for 26100). Do not hardcode the hex value; rely on the WDK headers compiled with the correct `NTDDI_VERSION`.

### 2. Mandatory vs Optional Callbacks (`DRIVER_INITIALIZATION_DATA`)
`dxgkrnl.sys` performs strict pointer validation *before* querying adapter capabilities. If any of the following "Mandatory" functions are `NULL`, `DxgkInitialize` will instantly fail with `STATUS_INVALID_PARAMETER`. 

You must provide at least stub functions returning `STATUS_SUCCESS` (or `STATUS_NOT_IMPLEMENTED` where appropriate, though `SUCCESS` prevents immediate tear-down during scaffolding).

**Absolutely Mandatory (Must be Non-NULL):**
*   **Initialization/PnP:** `DxgkDdiAddDevice`, `DxgkDdiStartDevice`, `DxgkDdiStopDevice`, `DxgkDdiRemoveDevice`, `DxgkDdiUnload`, `DxgkDdiSetPowerState`, `DxgkDdiQueryAdapterInfo`
*   **General/I-O:** `DxgkDdiDispatchIoRequest`, `DxgkDdiEscape`
*   **Interrupts:** `DxgkDdiInterruptRoutine`, `DxgkDdiDpcRoutine` *(Even if you don't fire interrupts yet, dxgkrnl expects these pointers)*
*   **Topology/Display:** `DxgkDdiQueryChildRelations`, `DxgkDdiQueryChildStatus`, `DxgkDdiQueryDeviceDescriptor`
*   **Memory/Allocation:** `DxgkDdiCreateAllocation`, `DxgkDdiDestroyAllocation`, `DxgkDdiDescribeAllocation`, `DxgkDdiGetStandardAllocationDriverData`, `DxgkDdiOpenAllocation`, `DxgkDdiCloseAllocation`, `DxgkDdiBuildPagingBuffer`
*   **Device/Context:** `DxgkDdiCreateDevice`, `DxgkDdiDestroyDevice`, `DxgkDdiCreateContext`, `DxgkDdiDestroyContext`
*   **Execution/Render:** `DxgkDdiPatch`, `DxgkDdiRender`, `DxgkDdiPresent` *(Even if you plan to use WDDM 2.0+ hardware scheduling, the base `Patch` and `Render` pointers must often be populated to pass the legacy validation block in `dxgkrnl` init)*.
*   **TDR (Timeout Detection):** `DxgkDdiResetFromTimeout`, `DxgkDdiRestartFromTimeout`
*   **VidPn Management:** `DxgkDdiIsSupportedVidPn`, `DxgkDdiRecommendFunctionalVidPn`, `DxgkDdiEnumVidPnCofuncModality`, `DxgkDdiSetVidPnSourceAddress`, `DxgkDdiSetVidPnSourceVisibility`, `DxgkDdiCommitVidPn`, `DxgkDdiUpdateActiveVidPnPresentPath`

**Optional (Can safely be NULL for minimal load):**
*   `DxgkDdiNotifyAcpiEvent`
*   `DxgkDdiControlEtwLogging`
*   `DxgkDdiFormatHistoryBuffer`
*   `DxgkDdiQueryCurrentFence` *(Optional on modern hardware scheduling WDDM 2.0+ driver setups, though recommended as a stub if scaffolding)*
*   `DxgkDdiSubmitCommand`, `DxgkDdiSubmitCommandVirtual` *(Mandatory ONLY IF your caps later declare hardware scheduling/virtual addressing, but `DxgkInitialize` allows them to be NULL at driver load time)*.

### 3. The Link Library Issue
The export for `DxgkInitialize` is located **strictly** in `dxgkrnl.lib`. 
`displib.lib` is exclusively a static helper library for DODs and **does not** export `DxgkInitialize`.

**If `dxgkrnl.lib` is missing from your `km\arm64` directory:**
This means your WDK installation for ARM64 is incomplete. `dxgkrnl.lib` is a standard WDK component.
1. Look in: `C:\Program Files (x86)\Windows Kits\10\lib\10.0.26100.0\km\arm64\dxgkrnl.lib`
2. If it is genuinely not there, run the Visual Studio Installer, modify your installation, and ensure **"Windows Driver Kit ARM64/ARM64EC build tools"** is explicitly checked. 
3. *Do not try to link `displib.lib` or `ntoskrnl.lib` to resolve `DxgkInitialize`.* It must be `dxgkrnl.lib`.

### 4. ARM64 cl.exe / link.exe Specifics
Since you are bypassing MSBuild, here are the strict requirements for an ARM64 full render KMD:

**cl.exe:**
*   `/arch:armv8.0` (Minimum baseline for Windows 11 ARM64).
*   `/D_ARM64_` and `/DARM64`.
*   `/DNTDDI_VERSION=0x0A00000F` (Critical so `dispmprt.h` pulls the WDDM 3.2 structs correctly).
*   `/GS` (Buffer security checks are mandatory in KM).

**link.exe:**
*   `/MACHINE:ARM64`
*   `/SUBSYSTEM:NATIVE`
*   `/DRIVER`
*   `/ENTRY:FxDriverEntry` (if using KMDF with WDDM) or `/ENTRY:DriverEntry` (if pure WDM/WDDM).
*   `/NODEFAULTLIB`
*   **Mandatory Link Libs:** `ntoskrnl.lib`, `hal.lib`, `wmilib.lib`, `dxgkrnl.lib`, and `BufferOverflowK.lib` (required for `/GS` in kernel mode on ARM64).

**ARM64 Architectural Specific (WDDM):**
Unlike x64, ARM64 has a weakly ordered memory model. When scaffolding your `DxgkDdiBuildPagingBuffer` and memory allocations, ensure you respect caching requirements. The OS will strictly check your `DXGK_ALLOCATIONINFO` caching flags (`WriteCombined`, `Cached`, etc.). Incorrect cache tags on ARM64 WDDM allocations will bugcheck `0x119` (VIDEO_SCHEDULER_INTERNAL_ERROR) much faster than on x86/x64.
