## Response

這是一個極具野心且硬核的專案！在 Windows on ARM (WoA) 上為 Raspberry Pi 5 的 V3D 撰寫 WDDM KMD，等同於從零重現顯示卡廠商的底層驅動團隊工作。你的整體策略（WDDM KMD -> D3DKMT -> v3dv UMD -> Zink/DXVK）在架構上是絕對正確且現代的。

以下針對你的問題提供具體、可操作的回答，並依照要求標註 **[確定]** 與 **[需查證]**。

---

### 1. WDDM KMD 的最小可行架構 (Render-Only)

**[確定]** WDDM 支援「Render-Only」設備（即不帶顯示輸出的純運算/渲染節點）。這在現代筆電（內顯負責 Display，獨顯負責 Render）已是常態。你可以實作一個不帶任何 `DxgkDdiCommitVidPn` 或 Display DDIs 的 WDDM KMD。

**必須實作的核心 DxgkDdi 回呼函數（最小集合）：**
*   **初始化與卸載：** `DxgkDdiAddDevice`, `DxgkDdiStartDevice`, `DxgkDdiRemoveDevice`, `DxgkDdiUnload`.
*   **Adapter/Device 建立：** `DxgkDdiCreateDevice`, `DxgkDdiCreateContext` (對應 GPU 內的 Context/Queue).
*   **記憶體管理 (VidMm)：** `DxgkDdiCreateAllocation` (分配 BO), `DxgkDdiDestroyAllocation`, `DxgkDdiBuildPagingBuffer` (建立分頁表更新指令).
*   **指令提交 (VidSch)：** `DxgkDdiSubmitCommandVirtual` (現代 WDDM 推薦使用虛擬定址提交).
*   **同步與中斷：** `DxgkDdiDpcRoutine` (處理 V3D 中斷), `DxgkDdiInterruptRoutine`, `DxgkDdiSignalMonitoredFence`.
*   **錯誤復原：** `DxgkDdiResetFromTimeout` (TDR).

**可 Stub (略過) 的功能：**
*   所有與 VidPn (Video Present Network) 相關的函數：`DxgkDdiRecommendVidPnTopology`, `DxgkDdiSetVidPnSourceAddress` 等，只要在驅動註冊時宣告不支援 Display 即可。
*   **[需查證]** WDDM 3.0 引入了 MCD (Microsoft Compute Driver) 專案（主要給 NPU 使用），但你要跑 Vulkan (v3dv)，可能仍需要註冊為標準的 Render Node (Graphics Driver) 而非純 Compute Driver，這點需要查閱 WDK 文件對 MCD 的限制。

### 2. 參考資源 (WDK 與開源實作)

這部分是最大的痛點，微軟**沒有**提供完整 3D 硬體渲染的開源範例，但社群有。

**[確定] 最佳開源真實 WDDM KMD 參考：virtio-gpu (viogpudo)**
*   **專案：** `virtio-win/kvm-guest-drivers-windows` (GitHub)
*   **路徑：** `/viogpudo` (舊版) 或 `/viogpu` (新版 DOD)。
*   **價值：** 這是目前唯一能在 Windows 上穩定運作、開源、且處理了 WDDM 記憶體分配與指令提交的驅動。雖然它是對虛擬硬體 (QEMU) 提交，但其架構（如何回應 dxgkrnl）完全符合你的需求。
*   **Mesa 關聯：** Mesa 裡面有 `winsys/virgl/vtest` 等實作，可以對照它如何將 UMD 映射到 viogpu WDDM。

**[確定] Microsoft WDK 官方範例：**
*   **專案：** `microsoft/Windows-driver-samples`
*   **目錄：** `video/KMDOD` (Kernel Mode Display Only Driver)。這是一個純顯示驅動，但提供了完美的 `DxgkDdi` 初始化、WDF (Windows Driver Framework) 註冊的 Boilerplate (樣板程式碼)。你可以用它當骨架，把 Display 的部分砍掉，換上 viogpudo 的 Render 邏輯。

**[需查證] Mesa 中的 D3DKMT 後端：**
*   Mesa 原始碼中的 `src/gallium/winsys/d3d12/wgl` 或是 Dozen (D3D12 over Vulkan) 包含了大量 UMD 如何呼叫 `D3DKMT*` 函數的實作。你必須在 Mesa 的 `v3dv` 中寫一個類似的 `v3dv_winsys_wddm.c`。

### 3. D3DKMT / dxgkrnl 介接 (UMD 到 KMD 的工作流)

**[確定]** 整個指令提交鏈條會是這樣：

1.  **UMD (Mesa v3dv)：** 在 Userspace 呼叫 `D3DKMTCreateAllocation` 申請一塊 Buffer 存放 CLE (Control List Executor) 狀態與指令。
2.  **UMD 提交：** UMD 將 CT0 (Binner) 和 CT1 (Render) 的指令寫入 Buffer，呼叫 `D3DKMTSubmitCommand` 或 `D3DKMTSubmitCommandToHwQueue`。
3.  **OS (dxgkrnl)：** 接收到請求，排程後呼叫 KMD 的 `DxgkDdiSubmitCommandVirtual`。
4.  **KMD (你的驅動)：**
    *   在 `DxgkDdiSubmitCommandVirtual` 中，你會拿到該指令的 GPU Virtual Address。
    *   你需要將這個地址寫入 V3D 的暫存器 (例如寫入 `V3D_CTnCA` 和 `V3D_CTnEA` 來啟動 Binner 或 Render 執行緒)。
    *   透過寫入 V3D 暫存器觸發硬體開始工作。
5.  **中斷 (Interrupt)：** V3D 跑完 CLE 後觸發 IRQ。你的 `DxgkDdiInterruptRoutine` 攔截到 IRQ，排程一個 DPC (`DxgkDdiDpcRoutine`)。
6.  **回報完成：** DPC 中呼叫 OS 提供的 callback (通知 Monitored Fence 已達成)，UMD 隨之得知任務完成。

### 4. VidMm / GpuMmu (記憶體管理)

**[確定] V3D 絕對適合 WDDM 的 `GpuMmu` 模型。**

*   V3D 擁有自己的 MMU（將 GPU VA 映射到 Physical Address）。
*   在 Linux DRM，驅動會在 `v3d_mmu.c` 中維護 Page Table (PTE)。
*   **在 WDDM 中：** OS 的 dxgkrnl (VidMm) 會負責分配實體記憶體並決定虛擬地址，然後呼叫 KMD 的 **`DxgkDdiBuildPagingBuffer`**。
*   **你的任務：** 當 OS 呼叫 `DxgkDdiBuildPagingBuffer` (夾帶 `DXGK_OPERATION_UPDATE_PAGE_TABLE` 指令) 時，你的 KMD 要將 OS 給的實體地址，轉換成 V3D 硬體看得懂的 Page Table Entry 格式，並寫入到 V3D 的 Page Table 記憶體中，最後清除 (Flush) V3D 的 MMU TLB (`V3D_MMU_CTL` 暫存器)。
*   **IoMmu** 模型是給依賴系統 SMMU（沒有自己 GPU MMU）的簡單硬體用的，V3D 不走這條路。

### 5. GPU 排程 / TDR 與 Preemption (搶佔)

**[確定] TDR 是強制的：**
Windows 對 GPU 假死非常敏感。如果 V3D 沒有在規定時間（預設 2 秒）內完成工作，OS 會呼叫 `DxgkDdiResetFromTimeout`。你必須在裡面重置 V3D 的硬體狀態 (Reset V3D core)。

**[需查證] Preemption (搶佔) 的最低要求：**
WDDM 2.x 的確要求 Preemption（例如在 Command Buffer 邊界搶佔），這是為了保證 Windows 桌面不會被耗時的 3D 渲染卡死。
*   **好消息：** V3D 硬體本身就支援 Job 級別的搶佔/中斷。
*   **Hack 作法：** 在初期開發（無 WHQL 認證需求下），你可以在 KMD 的 `DXGK_DRIVERCAPS` 中宣告只支援最粗粒度的搶佔（DMA Buffer Boundary），甚至在 OS 要求搶佔時，延遲回應直到當前任務結束。只要不引起 TDR，系統通常會容忍。

### 6. 務實評估 (Linux DRM 到 WDDM 的難度)

**[確定] 難度級別：Dark Souls 級別 (極高，但非不可能 / 10分滿分給9.5分)。**

如果在「一個人 + AI」的協作下：
*   **所需時間：** 全職投入預估需要 6 到 12 個月才能看到第一顆「畫出來的三角形」。
*   **主要雷區 (Pitfalls)：**
    1.  **WDDM 的囉嗦程度 (Verbosity)：** Linux DRM 的 `v3d_gem.c` 和 `v3d_sched.c` 加起來可能才幾千行程式碼。而在 WDDM 中，光是把 `DxgkDdi` 框架、VidMm 狀態機與 Paging Buffer 處理寫完並讓 dxgkrnl 載入不 BSOD (藍屏)，就需要上萬行 C/C++ 程式碼。
    2.  **缺少核心文件：** WDK 文件對於「如何精確實作 `DxgkDdiBuildPagingBuffer`」非常晦澀。很多欄位的意義只能透過逆向工程或猜測。
    3.  **同步機制 (Fences)：** Linux DRM 用 `dma_fence`，邏輯相對單向；WDDM 2.x 強度依賴 Monitored Fences 與 Hardware Queues，UMD 和 KMD 之間的同步狀態機極易寫錯導致系統死結。

**有沒有人做過類似的事？**
*   **社群：** 有人在做 Apple Silicon (M1/M2) 的 Windows 驅動，但圖形部分目前多依賴軟體渲染，硬體 3D (WDDM) 進展緩慢。
*   **Freedreno：** Qualcomm 的 Adreno Linux 開源驅動很成熟，但在 WoA 上，大家都是直接用 Qualcomm 官方的閉源 WDDM 驅動，很少人嘗試把 Freedreno 移植成 WDDM。
