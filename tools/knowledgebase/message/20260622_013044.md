## Response

這是一個非常硬核且關鍵的 Windows on ARM (WoA) 移植任務。HDMI 音訊在 SoC 平台上通常是顯示與音訊子系統高度耦合的產物。以下針對你的問題，提供務實的技術分析與架構建議：

---

### 1. BCM2712 HDMI 音訊硬體架構

**【事實與已知架構】**
*   **資料路徑 (Data Path)**：Host PCM Data → System Memory → **BCM2712 DMA Engine** → **MAI (Multichannel Audio Interface) FIFO** → **HDMI TX Audio Packetizer** → Data Island Packets (插入 Video Stream 的 blanking interval) → HDMI Sink。
*   **DMA 歸屬**：HDMI 是 Main SoC (BCM2712) 的原生功能，**完全不經過 RP1**，因此不涉及 PCIe 或 RP1 IOMMU。你必須使用 BCM2712 內建的 DMA controller (通常是 AXI DMA Engine) 來把記憶體中的 PCM 搬進 MAI FIFO。
*   **HDMI Controller**：BCM2712 延續 Pi 4 架構，核心依然是 Synopsys DesignWare (DW) HDMI TX IP 加上 Broadcom 自家的 wrapper (vc4)。
*   **Linux 對應 (vc4_hdmi.c)**：在 Linux 中，音訊被抽象為 ASoC DAI (Digital Audio Interface)。`vc4_hdmi_audio.c` 處理了 MAI 暫存器的配置。它依賴 `hdmi-codec` framework 來處理通用的 HDMI 音訊邏輯（如 InfoFrame 封裝）。

**【需要設定的關鍵參數 (與 Video 高度耦合)】**
*   **ACR (Audio Clock Regeneration)**：包含 `N` 與 `CTS` (Cycle Time Stamp) 暫存器。這是 HDMI 音訊的核心。Sink 端需要這兩個值，配合 Video Pixel Clock 來還原出 Audio Sample Clock (例如 48kHz)。**如果 Pixel Clock 變了，N/CTS 必須跟著變。**
*   **Audio InfoFrame**：包含 Channel count (2.0, 5.1)、Sample rate、Bit depth 等 metadata。
*   **Channel Status**：IEC60958 規範的 S/PDIF 狀態位元，告訴螢幕這是 PCM 還是 Compressed Audio (Passthrough)。

**【Pi 4 (BCM2711) vs Pi 5 (BCM2712) 差異】**
*   **推測/小幅差異**：基礎 IP 幾乎相同，最大差異在於 Base Address、Interrupt Routing，以及可能因為 BCM2712 新的記憶體架構 (16K page size ready / 內部 bus 頻寬) 導致的 DMA 描述符 (CB - Control Block) 格式或位址對齊要求的微調。

---

### 2. Windows 端架構（關鍵落差）

**【事實與務實選擇】**
*   *(b) 偽裝成 HDA codec？* **絕對不要。** 在軟體層面寫一個 Virtual PCIe Bus 加上 Virtual HDA Controller 加上 Virtual HDA Codec，工程量巨大且除錯會讓你崩潰。
*   *(a) 自寫 PortCls + WaveRT miniport？* **這是唯一務實且標準的作法。**
    *   在非 x86/PCIe 架構的 SoC 上（如高通 WoA 筆電），音訊驅動都是基於 `PortCls` (Port Class) 框架，並實作 `WaveRT` (Wave Real-Time) miniport。
    *   WaveRT 非常適合 DMA：它要求你配置一塊連續或 Scatter/Gather 的 Cyclic Buffer (環狀緩衝區)，硬體 DMA 不斷在裡面繞圈讀取，驅動只需定期更新 Position 暫存器。

**【音訊端點怎麼出現？】**
1.  你需要在 ACPI (DSDT) 中為 HDMI Audio MAI 定義一個 Device Node (例如 `BrcmHdmiAudio`)。
2.  你的 `PortCls` 驅動匹配這個 ACPI ID。
3.  驅動載入後，向 Windows 註冊一個 KS (Kernel Streaming) Filter。
4.  Windows 的 Audio Endpoint Builder 服務偵測到 KS Filter，就會在「控制台 -> 聲音」中建立一個「播放裝置」。
5.  **驅動分離度**：在 Windows 驅動模型中，**Audio Driver (PortCls) 與 Display Driver (DOD/WDDM) 是兩個獨立的 `.sys` 驅動**。

---

### 3. 與顯示 (DOD) 驅動的耦合 (最難搞的架構設計)

因為 HDMI 音訊封包是嵌在 Video TMDS/FRL 中的，**Audio Driver 無法獨立運作**。它必須知道 Pixel Clock 才能算 ACR，且如果螢幕進入休眠 (D3)，Audio 必須停擺。

**【務實做法：Kernel-Mode Private Interface】**
在 Windows 這是標準做法（類似 Intel 的 Display Audio 架構）。不要讓 Audio 驅動自己去 map HDMI MMIO，這會產生嚴重的 Race Condition。

1.  **DOD (Display) Driver 擁有 MMIO**：DOD 負責初始化 HDMI controller。
2.  **定義 Private Interface**：DOD 提供一組 function pointers（透過 `IRP_MN_QUERY_INTERFACE` 附帶自定義的 GUID 暴露出來）。
3.  **Audio Driver 呼叫 DOD**：
    *   `GetDisplayStatus()`: 螢幕是否亮著？EDID 支不支援音訊？
    *   `GetPixelClock()`: 取得當前 Pixel Clock（用來算 ACR）。
    *   `SetAudioState(Enable, SampleRate, Channels)`: Audio Driver 算好參數後，呼叫 DOD。**由 DOD 去寫入 HDMI TX 的 ACR、InfoFrame、MAI Enable 暫存器。**
4.  **Audio Driver 自己的職責**：只負責管理 System Memory 的 DMA Buffer，打 BCM2712 的 DMA Controller 暫存器，把 PCM 送進 FIFO，並處理 WaveRT Position 查詢。

---

### 4. 可行性 + 工程量 + 參考 + 第一個里程碑

**【工程量估算】**
*   對於熟悉 WDM/DMA 的 Windows 驅動工程師：**2 到 4 個月 (Man-Months)**。
*   最大未知數：
    1. BCM2712 DMA 的 WaveRT 適配（硬體 DMA 的 Position Reporting 精準度夠不夠？會不會產生 Glitch？）。
    2. DOD 與 Audio Driver 在 S3/S0ix/Screen Off 電源狀態切換時的同步 (Synchronization) 很容易藍屏或死鎖。

**【參考資源 (SOURCES)】**
1.  **Microsoft `sysvad` sample**: 這是聖經。裡面有一個 `Tablet` 範例，實作了純軟體的 WaveRT miniport。你要把它的 Dummy Buffer 替換成真實的 DMA 操作。
2.  **Linux `vc4_hdmi.c` & `vc4_hdmi_audio.c`**: 提取寫入 MAI、ACR 暫存器的 Magic Numbers 和順序。
3.  **HDMI Specification (1.4b 或 2.0)**: 必須看 Audio Clock Regeneration (N/CTS 計算公式) 與 Audio InfoFrame 封包結構的章節。

**【第一個里程碑順序 (Milestones)】**

*   **M1: 假驅動上線 (Dummy Endpoint)**
    *   編譯 `sysvad`，修改 INF 以匹配 ACPI ID。
    *   安裝後，Windows 系統匣出現喇叭圖示，可以選取「Pi 5 HDMI Audio」並播放音樂（雖然聽不到聲音，但 Windows Audio Engine 在跑）。
*   **M2: 跨驅動通訊 (IPC Setup)**
    *   實作 Audio Driver 向 DOD Driver 查詢 Interface。成功讀取到當前的 Pixel Clock (例如 148.5 MHz)。
*   **M3: 硬體暫存器點亮 (Tone Generator)**
    *   寫死 (Hardcode) 1080p60, 48kHz 的 N/CTS 值。
    *   在驅動裡手動建一個填滿 1kHz Sine Wave PCM data 的陣列。
    *   透過 DMA 送進 MAI。**目標：螢幕喇叭發出「嗶——」的長音。** (這證明硬體路徑通了)。
*   **M4: WaveRT 整合 (Play WAV)**
    *   把 Windows 傳下來的 WaveRT Ring Buffer 丟給 DMA。成功播放 Windows 開機音效。

---

### 5. VideoCore 韌體幫得上嗎？

**【事實與推測】**
*   **推測：幫不上大忙，且不建議依賴。**
*   **原因**：
    1.  Pi 的 Mailbox (Property tags) 歷史上主要是用來拿 EDID、設定 Framebuffer 解析度、調整 Clocks。
    2.  對應 HDMI Audio，Mailbox 沒有提供夠細粒度 (Fine-grained) 的動態控制介面來即時修改 Audio InfoFrame 或 ACR。
    3.  即使 Mailbox 能幫忙打開 HDMI 音訊總開關，**DMA buffer 的搬運、WaveRT 要求的高頻率 Position 查詢、Interrupt 處理，都發生在 Windows CPU 端 (ARM64)，韌體無法代勞。**
*   **務實建議**：把韌體當作「底層基礎建設」（負責把 HDMI HVS 跑起來）。音訊相關的 DW HDMI 暫存器 (MAI, Packetizer, InfoFrame)，透過你的 DOD Driver 直接打 MMIO 去控制，參考 Linux `vc4_hdmi_audio.c` 的邏輯是最穩妥的。
