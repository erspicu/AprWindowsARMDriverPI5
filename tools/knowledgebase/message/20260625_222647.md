## Response

這是一個非常硬核且具挑戰性的專案。將 Linux 驅動移植到 Windows on ARM (WoA)，尤其是針對 Raspberry Pi 5 這種全新架構（BCM2712 + RP1 架構），需要對 ACPI 與 Windows Driver Framework (WDF) 有深入理解。

以下針對你的問題提供具體、可操作的解答，並明確標示確定與需查證的部分。

---

### 1. worproject/rpi5-uefi 與 edk2-platforms 的關係與 Build 流程

**【確定】**
*   **關係：**
    *   `worproject/rpi5-uefi` 是 **Binary Release 與 Wrapper repo**。它包含預先編譯好的 `RPI_EFI.fd`、TF-A 韌體、設定檔（如 `config.txt`）以及用於打包這些 binary 的腳本。**不要 fork 這個來改 Code。**
    *   `worproject/edk2-platforms` 是 **Source Code Repo**（包含 ACPI ASL 檔與底層 C 語言驅動）。這是你自訂韌體需要 **Fork 與修改** 的地方。通常它會搭配官方 `tianocore/edk2` 主線一起編譯。
*   **Build 環境：** 強烈建議使用 **WSL2 Ubuntu 22.04/24.04**。

**【可操作步驟】**
1.  **安裝依賴：**
    ```bash
    sudo apt update
    sudo apt install build-essential uuid-dev iasl git gcc-aarch64-linux-gnu python3-distutils python3-pil python3-git
    ```
2.  **Clone 原始碼（【需查證】請確認 worproject 官方建議的 manifest 或 workspace 腳本，通常 WoR 會用 `mu_build` 或傳統的 `edk2` build）：**
    一般傳統流程會是建立一個 Workspace，把 `edk2`、`edk2-platforms`、`edk2-non-osi` 放在一起。
    ```bash
    mkdir ~/rpi5-uefi-workspace && cd ~/rpi5-uefi-workspace
    git clone https://github.com/tianocore/edk2.git
    git clone https://github.com/worproject/edk2-platforms.git # 確保切換到 rpi5 相關 branch
    git clone https://github.com/tianocore/edk2-non-osi.git
    ```
3.  **編譯指令（以傳統 EDK2 為例）：**
    ```bash
    export WORKSPACE=$PWD
    export PACKAGES_PATH=$WORKSPACE/edk2:$WORKSPACE/edk2-platforms:$WORKSPACE/edk2-non-osi
    export GCC5_AARCH64_PREFIX=aarch64-linux-gnu-
    source edk2/edksetup.sh
    make -C edk2/BaseTools
    build -a AARCH64 -t GCC5 -p Platform/RaspberryPi/RPi5/RPi5.dsc -b RELEASE
    ```
    *編譯產物會在 `Build/RPi5/RELEASE_GCC5/FV/RPI_EFI.fd`。*

### 2. ACPI vs Device Tree 與 ASL 檔案路徑

**【確定】**
*   **Windows on ARM 絕對依賴 ACPI**。Windows 的 `acpi.sys` 會解析韌體提供的 DSDT/SSDT 來列舉非即插即用（Non-PnP）的裝置並分配資源。DTB（Device Tree）在 Windows 無效。
*   **路徑：** BCM2712 的 ACPI 描述檔通常位於：
    `edk2-platforms/Silicon/Broadcom/Bcm2712/AcpiTables/` 或 `edk2-platforms/Platform/RaspberryPi/AcpiTables/`（取決於 WoR 團隊如何 refactor，尋找 `.asl` 副檔名，重點看 `Dsdt.asl` 或附屬的 `Mac.asl`、`Uart.asl`）。

**【可操作步驟：新增 ACPI 描述】**
要向 ACPI 註冊 SoC 裝置（例如 BCM2712 內建的 Watchdog 或 RNG），你需要在 DSDT 的 `\_SB` (System Bus) 下新增 Device 節點。

**範例：新增一個 MMIO 裝置 (BCM2712 SoC 內部)**
*   **_HID 慣例：** 可以自訂（如 `RPI5001`）或沿用現有（如微軟通用的 `MSFT8000` 配合 PWM）。
```asl
Device (WDOG) {
    Name (_HID, "RPI50001") // Hardware ID，你的 .inf 檔要 match 這個
    Name (_UID, 0)
    Method (_CRS, 0, Serialized) {
        Name (RBUF, ResourceTemplate () {
            // 記憶體映射 IO
            Memory32Fixed (ReadWrite, 0x10000000, 0x1000) // 【需查證】填入實際 BCM2712 WDOG 物理地址與長度
            // 中斷描述符
            Interrupt (ResourceConsumer, Level, ActiveHigh, Shared) { 123 } // 【需查證】填入 GIC SPI 中斷號
        })
        Return (RBUF)
    }
}
```

### 3. 關鍵問題：RP1 PCIe Endpoint 的處理策略

這是你整個專案架構的核心。RP1 是透過 PCIe 連接到 BCM2712 的南橋晶片。

**【方案對比】**

*   **做法 A：在 ACPI 中描述為 PCI 的 Child Device（韌體派）**
    *   **概念：** 讓 Windows 的 `pci.sys` 認出 RP1，但在 ACPI 的 PCIe Root Port 節點下，明確寫出 RP1 內部的 GPIO/I2C 控制器。
    *   **優勢：** 這是讓 Windows 的 SPB (Simple Peripheral Bus) 和 GPIO 框架完美運作的最佳解。如果你未來要用 ACPI 來描述連接在 RP1 I2C 上的感測器（透過 `I2cSerialBusV2` 巨集），該感測器必須在 ACPI 中能 reference 到 RP1 的 I2C 節點。
    *   **缺點：** ASL 撰寫極度複雜。你需要解析 PCIe BAR，並在 ACPI 中使用 `ADR` (Address) 來對應 PCIe Device/Function。

*   **做法 B：撰寫 KMDF PCI Bus Enumerator（驅動派 - 你最想做的）**
    *   **概念：** ACPI 中完全不寫 RP1 的內部細節。你寫一個 KMDF `sys` 檔，INF matching RP1 的 PCI Vendor ID / Device ID (例如 `PCI\VEN_14E4&DEV_2712` 【需查證實際 VID/PID】)。這個驅動啟動後，讀取 PCIe BAR 取得 RP1 的 MMIO 基址，然後使用 `WdfChildListCreate` 動態建立 PDO (Physical Device Objects) 給 GPIO, I2C 等子裝置。
    *   **優勢：** 完全不用改 UEFI ACPI！全在 Windows 核心態用 C 語言控制，除錯方便。
    *   **缺點：** 無法利用 ACPI 的 SPB 資源描述符。如果有一個觸控面板接在 RP1 I2C 上，你無法在 ACPI 裡寫 `I2cSerialBusV2 (..., \_SB.PCI0.RP1.I2C0)`，因為 ACPI 裡沒有那個 I2C0。觸控面板驅動也變成必須由你的 Bus Driver 動態 spawn。

**【業界標準與我的建議】**
*   **高通/Intel 的做法：** 由於高通的 SoC 高度整合，通常走 **做法 A (純 ACPI)**。但如果是外掛的複雜 PCIe 晶片，微軟標準做法是 **做法 B** (使用 `mf.sys` 多功能匯流排或自訂 KMDF Bus Driver)。
*   **給你的可操作建議：**
    既然你「不想改韌體，只想寫驅動」，**強烈建議採用 做法 B (KMDF PCIe Bus Driver)**。
    1. 寫一個 KMDF 驅動，掛載到 RP1 PCIe Endpoint。
    2. 驅動內部對 BAR 進行 Mapping。
    3. 針對 RP1 內部的 offset（例如 GPIO 區塊、I2C 區塊），動態 `WdfPdoInitAllocate` -> `WdfDeviceCreate`。
    4. 給這些 Child Devices 自訂 Hardware ID (例如 `RP1Bus\GPIO`、`RP1Bus\I2C0`)。
    5. 然後你再寫另外獨立的 KMDF 驅動去 match 這些自訂的 Hardware ID。
    *代價：連接在 RP1 上的周邊（如 I2C 感測器）也必須由你手動在驅動內 mapping 或提供自訂介面，不能依賴微軟標準 ACPI SPB 框架。*

### 4. 哪些可以純後裝 (pnputil)，哪些必須改 UEFI？

**【確定】**
這完全取決於硬體是如何掛載在 CPU 上的（是否具備**硬體發現機制 Hardware Discovery**）。

*   **可純後裝 (用 pnputil 載入，不動韌體)：**
    *   任何 USB 裝置。
    *   任何標準 PCIe 裝置（包括 RP1 本身！只要 PCIe Root Port 在 UEFI 中已經正確驅動，Windows 會自動掃描到 RP1，你可以直接對其 Vendor/Device ID 裝 `.sys`）。
    *   透過你自訂的 KMDF Bus Driver 動態 enumerated 出來的虛擬子裝置。
*   **【必須】改 UEFI ACPI 才能裝的裝置：**
    *   **BCM2712 SoC 內建的 MMIO 模組：** Mailbox、Watchdog、RNG、內建顯示控制器 (HVS) 等。因為這些模組只是一段存在於特定實體記憶體位址的暫存器，沒有 PCI/USB 那種配置空間 (Configuration Space)，Windows 核心根本不知道那裡有裝置。**必須透過 ACPI 的 `Memory32Fixed` 告訴 Windows。**

### 5. 捷徑：如何不重 Build 整包 UEFI 就載入 ACPI (SSDT Overlay)

如果你必須修改 BCM2712 的 ACPI，有一個極佳的 Windows 驅動開發捷徑，**不需要每次都編譯 EDK2 和重刷 SD 卡**。

**【確定：可操作的捷徑 - SSDT 動態載入】**
Windows 支援在開機期間動態載入 SSDT (Secondary System Description Table) 來擴充/覆寫 DSDT，這對驅動開發者是救星。

1.  **開啟測試模式 (Target Pi 5 Win11)：**
    ```cmd
    bcdedit /set testsigning on
    ```
2.  **在開發機上撰寫你的擴充 ASL：**
    建立一個 `my_bcm2712_devices.asl`，裡面只寫你要新增的 SoC 裝置。
    ```asl
    DefinitionBlock ("ssdt.aml", "SSDT", 2, "MSFT", "TEST", 1) {
        Scope (\_SB) { // 掛載到 System Bus 底下
            Device (RNG0) {
                Name (_HID, "RPI50002")
                Name (_CRS, ResourceTemplate () {
                    Memory32Fixed (ReadWrite, 0x10002000, 0x100) // 【需查證】RNG真實物理地址
                })
            }
        }
    }
    ```
3.  **編譯 AML 檔：**
    使用 Windows Driver Kit (WDK) 內建的編譯器：
    ```cmd
    asl.exe my_bcm2712_devices.asl
    ```
    這會產出 `ssdt.aml`。
4.  **在 Pi 5 Win11 上載入 AML (需 Admin 權限)：**
    將 `ssdt.aml` 丟到 Pi 5 上，然後執行 WDK 提供的 `asl.exe` (或用登錄檔工具)：
    ```cmd
    asl.exe /loadtable ssdt.aml
    ```
    重開機後，Windows 就會讀取這張 SSDT 假裝它是 UEFI 傳來的。你就可以打開「裝置管理員」，看到一個「未知的裝置」，Hardware ID 是 `RPI50002`，這時你就能用 `pnputil` 安裝你寫的 RNG KMDF 驅動了！

### 總結你的作戰計畫

1. **針對 RP1 上的周邊 (GPIO/I2C/SPI)：** 走 **做法 B**。寫一個 KMDF 驅動認 PCIe，動態 enumerate 出 I2C/SPI，然後用 `pnputil` 後裝它們的驅動。**完全不動韌體。**
2. **針對 BCM2712 SoC 直連的模組 (Mailbox/RNG/WDT)：** 寫一段獨立的 SSDT ASL 腳本，用 WDK 的 `asl.exe` 動態 inject 進 Windows。開發完成確定能動後，最後階段才把這些 ASL 節點整併回 `worproject/edk2-platforms` 的 `Dsdt.asl` 裡面重新 Build 一版最終的 `RPI_EFI.fd`。
