### 1. H4 封包型別與 Header 長度表 (H4 Packet Types & Header)

在 UART Read Pump 中，你需要一個精確的**狀態機 (State Machine)** 來解析位元流。H4 協議沒有 frame 的結尾標記，完全依賴 Header 中的 `Length` 欄位來決定 Payload 的大小。

#### H4 解析對照表

| H4 Type (1 byte) | 類型說明 | Header 總長度 (含自身嗎？否) | Payload Length 所在位移 (Offset) | Length 大小 / Endianness | 後續 Payload 讀取量 (Bytes) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **`0x01`** | **Command** | 3 bytes | Offset 2 | 1 byte | `Header[2]` |
| **`0x02`** | **ACL Data** | 4 bytes | Offset 2 ~ 3 | **2 bytes (Little-Endian)** | `Header[2] \| (Header[3] << 8)` |
| **`0x03`** | **SCO Audio** | 3 bytes | Offset 2 | 1 byte | `Header[2]` |
| **`0x04`** | **Event** | 2 bytes | Offset 1 | 1 byte | `Header[1]` |
| *`0x05`* | *ISO Data* (BT 5.2+) | *4 bytes* | *Offset 2 ~ 3* | *2 bytes (Little-Endian) ⚠️底層 14bits* | *依規範解析 (MVP 階段通常可忽略)* |

#### Read Pump 狀態機實作重點 (State Machine)
你的 RX 工作執行緒 (Worker Thread) 應該設計成 3 個主要狀態：
1. **`STATE_WAIT_TYPE`**: 讀取 1 byte。
   - 若為 `0x04`，進入 `STATE_WAIT_HEADER`，預期再讀 2 bytes。
   - 若為 `0x02`，進入 `STATE_WAIT_HEADER`，預期再讀 4 bytes。
2. **`STATE_WAIT_HEADER`**: 讀滿對應型別的 Header bytes。
   - 根據上表解析出 `PayloadLength`。
   - 分配/準備對應大小的 Buffer，進入 `STATE_WAIT_PAYLOAD`。
3. **`STATE_WAIT_PAYLOAD`**: 讀滿 `PayloadLength` 的 bytes。
   - 讀滿後，將完整封包（Type + Header + Payload）透過之前 pending 的 `IOCTL_BTHX_READ_HCI` 返回給 `bthport`。
   - 狀態重置回 `STATE_WAIT_TYPE`。

### 2. Bring-up 里程碑順序 (Milestones)

驅動開發最怕一團黑，必須像 WiFi bring-up 一樣設定明確的驗收點 (Go/No-Go criteria)：

*   **M1：基礎硬體就緒 (Hardware Init)**
    *   **動作**：Driver 載入，成功解析 ACPI/Device Tree，取得 UART handle 與 GPIO (BT_REG_ON, HOST_WAKE)。
    *   **驗證成功**：裝置管理員看到你的裝置節點無驚嘆號 (Code 10 允許，若故意 hold 住 D0Entry)；WPP Trace 顯示 `WdfIoTargetOpen` 成功。
*   **M2：晶片心跳測試 (First Alive Check) 🚀 第一個關鍵里程碑**
    *   **動作**：拉高 `BT_REG_ON`，等待 100ms。主動透過 UART 送出 HCI_Reset (`0x01 0x03 0x0C 0x00`)。
    *   **驗證成功**：UART RX 收到 Command Complete Event (`0x04 0x0E 0x04 0x01 0x03 0x0C 0x00`)。這代表 UART TX/RX 正常、Baud rate 正確（預設通常 115200）、晶片活著。
*   **M3：韌體下載與波特率切換 (.hcd Download & Baud Switch)**
    *   **動作**：送出 BCM Vendor Command 切換 Baud Rate (如 3Mbps)，Host 端 UART target 重新設定 Baud，接著分塊寫入 `.hcd`，最後再送一次 HCI_Reset。
    *   **驗證成功**：切換 Baud 後的 HCI_Reset 依然能收到 `0x04 0x0E...` 回應，證明韌體套用且高速 UART 穩定。
*   **M4：藍牙協定疊合 (BTHX Stack Binding)**
    *   **動作**：完成驅動初始化，回應 `bthport` 發來的 `IOCTL_BTHX_SET_VERSION`，並開始處理 `READ_HCI` / `WRITE_HCI`。
    *   **驗證成功**：Windows 右下角出現藍牙圖示；裝置管理員的「藍牙」類別下出現 "Bluetooth Radio"（代表 `bthport` 成功認領）。
*   **M5：實體連線與資料流 (Pairing & Data Flow)**
    *   **動作**：開啟 Windows 藍牙設定，掃描並配對裝置。
    *   **驗證成功**：配對一隻藍牙滑鼠或鍵盤，指標能動/字能打出來 (ACL 資料流動正確，Read Pump 沒漏 Byte)。

### 3. 電源管理 (Power Management)

藍牙在筆電/平板上是耗電大戶，且需支援 Connected Standby / Modern Standby。

*   **D0Exit (睡眠 / Sleep)**：
    *   **要不要拉低 BT_REG_ON？** **絕對不要（如果需要藍牙喚醒）**。在 Modern Standby (S0ix) 下，BT 晶片必須保持供電，並下發 Vendor Command 讓晶片進入 Sleep Mode (Low Power State)。如果系統進入 S4/S5 (休眠/關機)，則拉低 `BT_REG_ON` 關閉電源。
*   **D0Entry (喚醒 / Wake)**：
    *   如果從 S0ix 喚醒：UART 重新恢復通訊，**不需要**重載 `.hcd` (因為晶片沒斷電)。
    *   如果從 S4/S5 喚醒 (Cold Boot)：`BT_REG_ON` 重新拉高，**必須**重新走 M3 (載入 `.hcd` + Baud Switch)。
*   **BT_HOST_WAKE (OOB GPIO 中斷)**：
    *   **作用**：當 Host 處於低功耗 (UART 可能被關閉或休眠)，BT 晶片若收到配對裝置的封包（如滑鼠移動），會拉高 `BT_HOST_WAKE` 腳位。
    *   **處理**：驅動必須實作 **Arm-for-Wake** (`WdfDeviceAssignS0IdleSettings` / `EvtDeviceArmWakeFromS0`)。當 GPIO 中斷觸發時，WDF 會自動將裝置帶回 D0 狀態，你的 UART RX pump 恢復運作，讀取晶片發來的 Event。
*   **bthport 的 IOCTL_BTHX 電源指令**：
    *   `bthport` **不會**發送專門的「Power Off IOCTL」。它是透過標準的 `HCI_Reset` 或是改變掃描狀態的 HCI Command 來控制。
    *   無線電開關 (Airplane Mode / Radio Management) 主要是透過 `bthport` 停止發送 HCI 指令並斷開連線，你的驅動只需忠實傳遞 HCI Command 即可。

### 4. SCO/eSCO (藍牙音訊) 處理策略

*   **A2DP (聽音樂 / 追劇)**：走的是 ACL 封包 (`0x02`)。資料會經過 UART，你的 Read Pump 會處理到它。只要 UART 頻寬夠 (3Mbps)，A2DP 就能完美運作。
*   **SCO / eSCO (語音通話 / 麥克風 HFP)**：走的是 SCO 封包 (`0x03`)。
    *   **硬體架構差異**：在 ARM64 SoC (如 Snapdragon / RK3588) 的設計中，SCO **通常不走 UART**。因為 UART 延遲太高，語音會斷續。硬體上，BT 晶片會有實體的 PCM/I2S 線路直接連到 SoC 的 Audio Codec。
    *   **MVP 階段建議**：**不管它**。
    *   **實作細節**：當 `bthport` 詢問 Capability 時（如果有相關查詢，或透過 INF 宣告），宣告音訊繞道 (Sideband Audio / PCM routing)。如果 Read Pump 真的收到 `0x03` 的封包，按照長度讀完並原封不動丟給 `bthport` 即可，但大部分情況下，BCM 晶片需要透過 Vendor HCI Command (`Write_SCO_PCM_Int_Param` 之類的) 告訴晶片「把通話語音路由到實體 I2S 腳位，不要發給 UART」。

### 5. 仍待驗證 / 實機釐清清單 (Checklist & Uncertainties) ⚠️

在真正開始敲代碼/上機前，這些是你需要查閱 WDK 或在實機上摸索的「盲點」：

| 分類 | 待查/待確認項目 | 為什麼重要？ |
| :--- | :--- | :--- |
| **BTHX API** | ⚠️ `bthx.h` 中的 `BTHX_HCI_READ_WRITE_CONTEXT` 確切定義。 | 這是你回傳給 `bthport` 封包時必須填寫的 metadata (包含 Data Length 與 Type)。 |
| **BTHX API** | ⚠️ `IOCTL_BTHX_SET_VERSION` 的雙向溝通。 | Windows 支援哪些 BTHX 版本？你的驅動要回報支援哪個版本才能讓 bthport 滿意？ |
| **INF 設定** | ⚠️ `INF` 檔的 `Needs` 與 `Include` 寫法。 | 傳統 USB 藍牙是 `Needs=BthUsb.NT`。你的 BTHX 驅動是否需要 `Include=bth.inf` 並指定 `Needs=BthUart.NT` 或自訂？這決定了 Windows 藍牙核心堆疊是否會掛載到你頭上。 |
| **BCM 韌體** | ⚠️ Broadcom 特殊的 `.hcd` 下載協定。 | 下載指令是 `0x01 0x2E 0xFC` (`Download_Minidriver`) 嗎？每次寫入 Payload 的 Chunk Size 上限是多少（通常是 252 bytes）？ |
| **休眠機制** | ⚠️ UART RTS/CTS (硬體流量控制) 在 D0Exit 時的行為。 | 進入睡眠前，Host 的 UART RTS 是否要拉高 (告訴 BT 不要再傳資料)？如果沒處理好，BT 晶片在 Host 睡著時灌資料會導致系統藍屏或 UART 暫存器溢位。 |
| **MAC Address** | ⚠️ BCM 晶片的 MAC Address 來源。 | 很多 ARM 平台沒有將 MAC 燒進 OTP，而是開機時由 ACPI 讀取或 Registry 給予，再透過 Vendor Command (`0x01 0x01 0xFC`) 寫入晶片。你的驅動需要負責這段嗎？ |

**總結開發節奏建議**：
請嚴格遵守 **M1 -> M2** 的順序。在寫出完整的 WDF / BTHX 架構前，**先寫一個簡單的 WDF 驅動，只做開 UART、拉 GPIO、送 HCI_Reset 並印出 DbgPrint**。只要能看到 `0x04 0x0E...` (M2 達成)，剩下的就是體力活（疊 BTHX、抄狀態機、處理 .hcd）了。
